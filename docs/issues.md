## 🟢 #1 — 발목 IK 두 모터 각도의 규약


**어디서**: `kinematics/ankle.py` 를 쓰면서. 모터가 보고하는 범위와 IK 가 내는 범위를 맞추다가
**해결됨** — `kinematics/ankle.py` 가 두 각도를 모두 `[-180, 180)` 으로 냄.

### 무엇이었나

두 모터 각도를 서로 다른 범위로 내면 한쪽이 모터의 보고 범위와 어긋남.

| | IK 반환 | 모터가 보고 (`zero_sta=1`) |
|---|---|---|
| `a1` (m11) | `[0, 360)` | `[-180, 180)` |
| `a2` (m12) | `[-180, 180)` | `[-180, 180)` |

`a1` 이 -5도 근처면 355도가 되는데, 그 값은 모터의 한계 밖임. IK 가 340도를
돌려주고 모터가 -20도를 보고하면 **360도 차이**가 남.

### 근거

RS02 매뉴얼 p.27 `0x7029 zero_sta` — 1로 설정 시 위치 보고 범위가 `-π ~ π`.
본 프로젝트는 `zero_sta = 1` 임.

### 조치

`_wrap180()` 하나로 두 각도를 같이 접음. `TestSolveIk` 의
`test_both_angles_are_in_one_convention` 이 시험 자세 8개에 대해 고정함.

### 같은 규약을 raw ↔ cal 변환에도 씀

`cal = sign x raw + offset` 은 산수라 **경계의 건너뜀이 그대로 통과함.** 영점이
raw 의 `±180` 근처에 잡힌 관절을 `sweep` 하면 이렇게 나옴.

```
     raw      cal        lo       hi     span
   179.0      9.0       0.0      9.0      9.0
  -177.0   -347.0    -347.0      9.0    356.0
```

40도 움직인 것이 356도 범위로 기록되고, 한계 가드도 `-347` 을 보고 엉뚱하게 자름.

`motors/base.py` 의 `wrap180` 을 `raw_to_cal` / `cal_to_raw` 양쪽에 넣음. `sweep` 도
같은 함수를 씀. `cal_to_raw` 를 접는 이유는 명령이 모터가 보고하는 범위 안으로
나가야 하기 때문임.

전제는 관절이 한 바퀴를 돌지 않는 것임 — 영점에서 `±180` 안에 전 가동 범위가
들어와야 함. 다리 관절은 전부 그러함. 그래서 별도의 각도 감싸기 계층
(`safety/wrap.py`)은 필요 없음.

## 🟢 #2 — 한계값이 raw 공간인지 cal 공간인지


**어디서**: `motors/base.py` 의 `MotorCalibration` 을 설계하면서. 한계를 어느 자료형에 둘지 정하다가
**결론: cal 공간, 캘리브레이션 파일.** `commission sweep` 이 재서 적음.

### 두 공간

raw 는 모터가 CAN 으로 보고하는 각도임. 기준점은 그 모터의 기계 영점이고, 그건
사람이 `0xFE` 를 누른 그 순간의 자세임.

cal 은 사람과 기구학이 말하는 관절 각도임. 기준점은 우리가 정한 자세임.

    cal = sign * raw + offset

어긋나는 원인은 둘임.

**기준 자세가 다름 (`offset`)** — 다리가 무거워 `0xFE` 를 정확히 편 자세에서 누를
수 없음. 무릎을 12도 굽은 상태에서 영점 잡으면:

| 물리적 자세 | raw | cal |
|---|---|---|
| 완전히 편 상태 | -12 | 0 |
| 12도 굽힘 (영점 잡은 자세) | 0 | 12 |
| 하드스톱 | 62.79 | 74.79 |

**회전 방향이 다름 (`sign`)** — 양다리는 거울상이라, 같은 굽힘에 대해 한쪽은 CW
한쪽은 CCW 로 돔.

| 물리적 자세 | 오른 무릎 raw | 왼 무릎 raw | cal (양쪽 동일) |
|---|---|---|---|
| 편 상태 | 0 | 0 | 0 |
| 45도 굽힘 | +45 | -45 | 45 |

이것이 cal 공간이 존재하는 이유임. 보행 궤적이 "무릎 45도" 라고 하면 양다리가 같은
동작을 함. raw 로 말하면 다리마다 부호를 뒤집어야 하고, 그걸 잊는 자리가 코드
곳곳에 생김.

감속비 항은 없음 — RobStride 는 출력축 각도를 보고하므로 배율이 필요 없음.

### 무엇이 문제였나

한계값을 raw 로 볼지 cal 로 볼지, 그리고 어느 파일에 둘지가 정해지지 않아 비교하는
쪽마다 다른 공간의 값을 맞대고 있었음. 지금은 `sign=1, offset=0` 이라 `cal == raw`
로 두 공간이 같은 숫자임. **어느 쪽으로 해석해도 똑같이 동작하므로 드러나지 않음.**
`commission sweep` 이 `offset_deg` 를 넣는 순간 갈라짐.

### 공간: cal

한계는 관절 좌표계 값임. `commission sweep` 이 관절 0도를 **먼저** 정하고 그 기준으로
최대·최소를 기록하므로, 나온 값이 곧 cal 공간 값임.

raw 로 적으면 영점을 다시 잡을 때마다 숫자가 바뀜. cal 로 적으면 기계 영점이 옮겨간
만큼 `offset_deg` 가 흡수함 — 단, 둘 다 같은 조작에서 나오므로 영점을 다시 잡으면
둘 다 다시 재야 하는 것은 같음.

`lo < hi` 를 `__post_init__` 에서 검사함. cal 공간에는 `sign` 이 개입하지 않아 순서가
뒤집히지 않으므로, 변환할 때마다 `min/max` 로 재정렬할 필요가 없어짐.

`None` 은 "제한 없음" 이 아니라 "아직 안 잼" 임. `Motor.is_configured` 가 False 가
되어 상위에서 제어 진입을 막음.

### 자리: 캘리브레이션 파일

한계는 **재는 값**임. `commission sweep` 이 토크를 끄고 관절을 손으로 양쪽 끝까지
미는 동안 기록함. 발목은 발을 잡고 움직이면 두 모터가 같이 따라오므로 한 조작으로
두 범위가 같이 나옴.

같은 조작에서 `offset_deg` 와 `limits_deg` 가 같이 나오고, 기계 영점을 다시 잡으면
둘 다 무효가 됨. **한쪽만 갱신되는 상태가 있으면 안 되므로 같은 파일에 둠.**

`robot.yaml` 에는 사람이 손으로 적는 값만 남음 — `id`, `model`, 게인. 그 파일은
주석이 많아서 프로그램이 다시 쓰면 주석이 전부 날아감. 그래서 프로그램은 JSON 만 씀.

`robot.yaml` 에 `limits_deg` 를 적으면 로더가 거부함. 같은 값이 두 군데 있으면
어긋났을 때 어느 쪽이 진짜인지 알 수 없음.

게인만 예외임. 실물에서 찾는 값이지만 사람이 주석과 함께 손으로 적는 값이라
`robot.yaml` 에 둠 (이슈 #9).

### 조치

    motors/base.py              MotorCalibration.limits_deg (cal 공간, Optional)
    calibration/store.py        읽고 씀. schema_version 2
    config/loader.py            robot.yaml 의 limits_deg 를 거부함
    robots/leg.py               캘리브레이션의 한계를 Motor.limits_deg 로 옮겨 넣음
    scripts/commission.py       sweep 이 재서 바로 적음

가드는 `Motor.limits_deg` 하나만 봄. `Leg` 가 캘리브레이션을 붙일 때 설정 사본에
옮겨 넣어, 읽는 자리를 한 군데로 유지함.

## 🟢 #3 — `calibrate()` 와 `is_calibrated` 가 `Robot` 계약에 있음


**어디서**: `robots/base.py` 의 `Robot` 계약을 정하면서
**해결됨** — `robots/base.py` 의 `Robot` ABC 에 둘 다 추상 멤버로 넣음.

### 왜 계약에 있어야 하나

각 로봇이 제멋대로 판정하면 호출부가 **"이 로봇은 준비됐나" 를 물어볼 공통 방법이
없어짐.** 미실측 상태로 토크를 넣는 것이 가장 위험한데, 그걸 막는 판정이 구현마다
다르면 막히지 않는 구현이 하나쯤 생김.

`Leg` 만 이 판정을 가지면 `Humanoid` 나 `Arm` 이 생길 때 각자 다시 만들게 되고,
호출부는 타입을 보고 분기해야 함.

### 지금 구조

    Robot.is_calibrated     추상 프로퍼티
    Robot.calibrate()       추상 메서드

`Leg` 의 구현은 **둘 다** 봄.

    config.is_configured            한계와 게인이 채워졌는지
    not unmeasured(calibration)     영점 메모가 남아 있는지

게인만 있으면 어디까지 가도 되는지 모르고, 한계만 있으면 토크가 안 나감.

`Leg.enable()` 이 이 판정을 보고 거부함. 커미셔닝 단계에서는
`allow_uncalibrated=True` 로 만들면 경고만 하고 진행함 -- 실측 전에도 움직여야
실측을 할 수 있기 때문임.

`calibrate()` 는 파일을 다시 읽는 것까지만 함. 재는 절차 자체는 사람이
`scripts/commission.py` 로 함.

## 🟢 #4 — 관측이 제어 경로와 같이 감


**어디서**: `telemetry/` 를 만들면서. 어느 경로에서 부르든 같은 값이 나와야 한다는 것을 정리하다가
**해결됨** — `control/loop.py` 가 매 주기 기록하고, `scripts/bringup.py` 의 움직이는
항목이 전부 그 루프를 탐.

### 무엇이었나

관측 경로가 제어 경로와 따로 놀면, 사람이 손으로 움직여 볼 때는 그래프가 안 나오고
자동 제어 때만 나옴. **게인을 튜닝하려면 손으로 움직이면서 봐야 함.**

메뉴가 로봇을 직접 부르면 그 경로에서만 다음이 빠짐.

    텔레메트리 (UDP·CSV)
    주기 측정 (loop_dt, overruns, kept_up)
    정지 순서 (hold 후 토크 차단)

그러면 그래프가 안 나오는데 **텔레메트리가 고장난 줄 알게 되고**, 같은 일을 하는
코드가 두 벌이 되어 한쪽만 고쳐짐.

### 지금 구조

    menu -> motion -> ControlLoop -> Leg -> bus

메뉴 항목은 `Motion` 만 정하고 `_run()` 에 넘김. `_run()` 이 모드를 CONTROL 로
바꾸고 루프를 돌린 뒤 관찰 모드로 되돌림.

`snapshot.build()` 는 `Robot` 계약만 쓰므로 어느 경로에서 부르든 같은 값이 나옴.

### 고정한 것

`tests/test_bringup.py` 의 `TestGoesThroughTheLoop` 가 `ControlLoop.run` 을 감시함.
움직이는 항목이 루프를 타지 않으면 실패함.

### 예외

되돌리기 어려운 조작(영점, CAN id, 프로토콜)은 `scripts/commission.py` 에 있고
루프를 타지 않음. **반복하지 않는 조작이라 주기가 없음.**

## 🟢 #5 — 종류·개체·기하를 나눔


**어디서**: `config/schema.py` 의 `LimbConfig` 를 설계하면서. 팔이 붙으면 무엇이 달라지는지 따져 보다가
**해결됨** — `config/schema.py` 의 `LimbConfig` 가 셋을 따로 가짐.

### 무엇이었나

값 하나가 세 가지를 겸하면 확장할 때 막힘.

    종류   어떤 기구학을 쓰는지        다리냐 팔이냐
    개체   이 로봇에서 부르는 이름     같은 종류가 둘 이상일 때 구분
    기하   거울상인지                  좌우 대칭 여부

허리처럼 좌우가 없는 부위가 생기면 "왼쪽도 오른쪽도 아님" 을 표현할 수 없음.

### 지금 구조

    limbs:
      right_leg:        <- 개체 이름. 사전의 키
        kind: leg       <- 종류
        side: right     <- 기하. 없어도 됨

개체 이름을 키로 둔 것은 같은 이름이 둘일 수 없게 하려는 것임.

`side` 는 "거울상이다" 라는 사실만 적음. **실제 부호 뒤집기는 캘리브레이션의
`sign` 이 함** -- 그건 재서 얻는 값이라 설정에 올 수 없음. 발목 링키지의 거울상은
`AnkleGeometry.mirrored()` 가 따로 다룸.

`RobotConfig.limbs_of_kind("leg")` 로 종류별로 골라낼 수 있음. 팔이 붙어도 그대로
동작함.

## 🟢 #6 — 컨텍스트 매니저


**어디서**: `motors/canbus.py` 를 쓰면서. 제어 중 예외가 나면 무엇이 남는지 따져 보다가
**해결됨** — 세 계층 전부에 있음.

    CanBus       __enter__ / __exit__
    MotorsBus    ABC 에 기본 구현
    Robot        ABC 에 기본 구현

### 왜 필요한가

제어 중 예외가 나면 **모터가 마지막 명령을 계속 유지함.** 명령을 갱신하는 코드가
죽었으므로 사람이 전원을 뽑을 때까지 다리가 힘을 주고 있음.

    with leg:
        leg.enable()
        raise RuntimeError(...)     # 여기서 터져도 토크가 끊김

### 정리 순서

`RobStrideBus.disconnect()` 가 **토크를 먼저 끊고** 채널을 닫음. 순서가 반대면
채널이 닫힌 뒤라 정지 명령을 보낼 방법이 없어짐.

토크 차단이 실패해도 채널은 반드시 닫음 -- 여기서 예외를 올리면 정리가 중간에 멈춰
소켓이 열린 채로 남고, 다음 실행 때 채널을 못 엶.

### 고정한 것

    test_disconnects_even_on_exception          MotorsBus
    test_context_manager_closes_on_exception    CanBus
    test_disconnect_stops_torque_before_closing RobStrideBus
    test_context_manager_disconnects_on_exception  Leg

`__del__` 은 두지 않음. 가비지 컬렉션 시점이 정해져 있지 않아 언제 끊길지 알 수
없고, 인터프리터 종료 중에는 import 가 이미 정리되어 동작을 보장할 수 없음.

## ⚪ #9 — 게인이 튜닝 전 시작값임


**어디서**: `config/robot.yaml` 에 게인 칸을 만들면서
### 무엇

오른다리 게인이 `kp = 20.0`, `kd = 1.0` 이다. 실물에서 찾은 값이 아니라
**어디서부터 올리고 내릴지의 출발점**이다.

왼다리는 `kp = 0` 이다. 한계를 모르는 관절에 게인만 넣으면 어디까지 가도 되는지

### 영향

너무 크면 다리가 튀고 너무 작으면 중력에 처지는데, 어느 쪽인지는 돌려 보기
전까지 모른다. 값이 들어 있으면 튜닝이 끝난 것처럼 보이는 것이 이 항목의 위험이다.

`kp = 0` 이면 토크가 항상 0이다. 프레임은 나가는데 모터가 전혀 힘을 주지 않는다.
`Motor.is_configured` 가 `kp > 0` 을 요구하는 이유가 이것이다.

### 조치

`huphy-bringup --gain-scale 0.1` 로 낮춰 시작해 계단 응답을 보며 찾는다.
목표를 지나쳤다 돌아오면 `kd` 가 부족하고, 못 미치면 `kp` 가 부족하고, 부르르
떨면 `kp` 가 과하다.

찾은 값을 `robot.yaml` 에 적고, `huphy-test zero` 와 `range` 로 다리 전체가
버티는지 본다.

## 🟢 #10 — 계산·전송·수거를 나눔

**해결됨** — 두 계층에서 나뉨.

    CanBus.send_many / drain / drain_all
    Leg.build_commands / send / collect / send_action

### 무엇이었나

세 가지를 한 함수가 하면 버스가 둘일 때 두 다리의 명령 시각이 벌어짐.

    can0 (왼다리)  [계산][전송][─── 수거 대기 ───]
    can1 (오른다리)                                [계산][전송]
                                                   ^ 여기서야 시작

두 버스는 물리적으로 독립이라 진짜로 겹쳐 보낼 수 있는데 그 병렬성을 못 씀.
**수거가 더 비쌈** -- `recv()` 는 큐가 비면 타임아웃만큼 블로킹함.

### 지금 구조

    left = left_leg.build_commands(action_left)     # 계산은 CAN 을 안 씀
    right = right_leg.build_commands(action_right)
    left_leg.send(left)                              # 전송을 몰아서
    right_leg.send(right)
    left_leg.collect()                               # 그 다음에 수거
    right_leg.collect()

다리 하나뿐이면 `send_action()` 하나로 충분함 -- 셋을 순서대로 부름.

### 고정한 것

    test_build_does_not_touch_can      계산이 프레임을 안 보냄
    test_send_all_precedes_drain_all   전송이 수거보다 먼저 (버스 공유 이벤트 순서)

### 남은 것

지금은 순차 전송이라 프레임 6개 사이의 지연(약 0.8 ms)은 남음. 양다리에서 이것이
문제가 되면 버스마다 수신 스레드를 두어 제어 루프에서 수거를 없애야 함. 그때
`canbus.py` 의 락 구성을 다시 봐야 함.

## 🟢 #12 — 기계 영점(`0xFE`)의 지속성


**어디서**: `scripts/commission.py` 의 `zero` 명령을 설명하면서
**해결됨** — 사용자가 실물에서 확인함. 전원을 끊었다 켜도 영점이 유지됨.

### 무엇이었나

`tables.py` 의 주석에 지속성에 대한 언급이 없었음.

    CMD_SET_ZERO = 0xFE      # Command 4. 비위치 모드에서만 동작

같은 모터의 `PARAM_ZERO_STA`(`0x7029`) 는 별도의 저장 명령이 있어야 유지되므로
(`tables.py` 주석의 "Type 22로 저장해야 유지됨"), `0xFE` 도 그럴 가능성이 있었음.

### 왜 중요했나

**절차가 통째로 달라짐.**

| 남는 경우 | 안 남는 경우 |
|---|---|
| 조립할 때 한 번 잡으면 끝 | 전원을 켤 때마다 다시 잡아야 함 |
| `offset` 실측이 의미 있음 | 매번 같은 자세를 재현해야 함 |
| `zero_reference` 메모가 재조립용 | 메모가 매일 쓰는 절차서가 됨 |

안 남는 쪽이었다면 `zero` 를 커미셔닝이 아니라 시작 절차에 넣어야 했음.

### 결론

남으므로 `commissioning.py` 에 두는 것이 맞음. `zero_reference` 메모는 모터를
교체하거나 재조립할 때 같은 자세를 재현하는 데 씀.

## 🟢 #14 — 한계 여유의 방향

**어디서**: `safety/limits.py` 를 쓰면서. 여유를 어느 쪽으로 두는지 정하다가

### 무엇

`limits_deg` 는 **하드스톱 그 자체**임. 여유를 이미 뺀 값이 아님.

따라서 여유는 **안쪽으로** 좁혀야 함.

```python
def safe_window(limits, margin_deg):
    lo, hi = limits
    m = abs(margin_deg)
    return lo + m, hi - m        # 안으로
```

바깥으로 더하면 한계 밖 몇 도까지 허용하게 되어, 여유가 **보호가 아니라 확장**이 됨.

### 여유가 왜 필요한가

세 가지를 흡수함.

```
오버슛     명령이 한계에 딱 붙어 있으면 지나침
관성       무거운 다리는 목표에서 바로 멈추지 않음
측정오차   위치 해상도가 0.022도이고 캘리브레이션 오차도 있음
```

지금 3도는 임의로 잡은 출발점임. **게인을 튜닝하면 필요한 값이 달라짐** — 오버슛이
줄면 여유도 줄일 수 있음.

## 🟢 #15 — 한계를 넘는 명령을 자름

**어디서**: `safety/guards.py` 를 쓰면서. 넘는 명령을 어떻게 다룰지 정하다가

### 무엇

한계를 넘는 명령을 **버리지 않고 자름.**

### 왜

버리면 그 모터만 직전 명령을 유지함. 다른 관절은 새 명령대로 움직이는데 하나만
멈춰 있으면 **다리 자세가 어긋남.**

발목처럼 두 모터가 하나의 관절을 만드는 곳에서 특히 나쁨 — 한쪽만 멈추면 두 로드가
서로 다른 자세를 요구함.

자르면 한계까지는 감. 먼 목표도 여러 주기에 걸쳐 결국 도달함 — **클리핑이 곧 속도
제한**이 됨.

### 자른 것은 반드시 알림

클리핑은 **조용한 변조**임. 명령한 것과 다른 게 실행되므로 무슨 일이 있었는지 함께
돌려줌.

```python
GuardResult(value=71.79, clips=(ClipReason.LIMIT,))
```

카운터로 쌓여 텔레메트리로 나감. `since_clip` 으로 **언제** 일어났는지도 봄.

### 버리는 경우도 있음

NaN 과 현재 위치를 모르는 경우는 **클리핑으로 고칠 수 없어** 버림.

```
NaN     자를 대상이 없음. min/max 가 통과시킴
위치 모름  점프를 잴 기준이 없음
```

| 조합 | 위치 | 속도 | 토크 | 매뉴얼 |
|---|---|---|---|---|
| RS02 / MIT | ±12.57 rad | **±33 rad/s** | ±17 N·m | p.37~38 |
| RS02 / private | ±12.57 rad | **±44 rad/s** | ±17 N·m | p.20~21 |
| RS00 / MIT | ±12.57 rad | ±33 rad/s | **±14 N·m** | Command 3 표 |

**토크는 모델마다 다름.** 발목이 RS00, 나머지가 RS02 라 한 다리 안에서도 갈림.
`tmax` 가 틀리면 토크가 그 비율만큼 어긋나는데, 위치 제어에서는 `tau_ff=0` 만
보내서 드러나지 않음 — 0은 어느 범위에서도 같은 정수(2047)로 나감.

무부하 410rpm ≈ 43 rad/s 이므로 private 은 전 범위를, MIT 은 12bit 라 ±33 으로
잘라 쓰는 것으로 보임.

### 왜 중요한가

**틀리면 속도 읽기가 44/33 = 1.33배 어긋남.** 위치와 토크는 영향 없어서 눈에 잘
안 띔.

```python
u = float_to_uint(10.0, -33.0, 33.0, 12)
uint_to_float(u, -33.0, 33.0, 12)     # 10.0   맞음
uint_to_float(u, -44.0, 44.0, 12)     # 13.33  1.33배
```

### 조치

인코딩 표를 `[프로토콜][모델]` 로 인덱싱함. "모델별 사양" 하나로 뭉치면 private
값을 MIT 에 가져다 쓰는 실수가 남.

**없는 조합에 `KeyError` 를 던짐.** 조용히 기본값으로 때우지 않음 — 범위가 틀리면
명령한 값과 실제가 배율만큼 어긋나는데, 실물에서 찾기 매우 어려움.

현재 MIT 만 쓰지만 `PRIVATE_ENCODING` 도 표에 남김. **두 범위가 다르다는 사실
자체가 중요함.**
