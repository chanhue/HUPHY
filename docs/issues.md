## 🟢 #1 — 발목 IK 두 모터 각도의 규약


**어디서**: `kinematics/ankle.py` 를 쓰면서. 모터가 보고하는 범위와 IK 가 내는 범위를 맞추다가
**해결됨** — `kinematics/ankle.py` 가 두 각도를 모두 `[-180, 180)` 으로 냄.

### 무엇이었나

두 모터 각도를 서로 다른 범위로 내면 한쪽이 모터의 보고 범위와 어긋남.

| | IK 반환 | 모터가 보고 (`zero_sta=1`) |
|---|---|---|
| `a1` (m11) | `[0, 360)` | `[-180, 180)` |
| `a2` (m12) | `[-180, 180)` | `[-180, 180)` |

`a1` 이 -5도 근처면 355도가 되는데, 그 값은 모터의 한계 밖임. IK 가 340도를
돌려주고 모터가 -20도를 보고하면 **360도 차이**가 남.

### 근거

RS02 매뉴얼 p.27 `0x7029 zero_sta` — 1로 설정 시 위치 보고 범위가 `-π ~ π`.
본 프로젝트는 `zero_sta = 1` 임.

### 조치

`_wrap180()` 하나로 두 각도를 같이 접음. `TestSolveIk` 의
`test_both_angles_are_in_one_convention` 이 시험 자세 8개에 대해 고정함.

이 규약이 맞아떨어져서 각도 감싸기 처리(`safety/wrap.py`)가 필요 없어짐 — 모든
관절 한계가 ±180 안에 있고 전 회전을 하지 않으므로, 두 공간의 규약만 맞으면 됨.

## 🟢 #2 — 한계값이 raw 공간인지 cal 공간인지


**어디서**: `motors/base.py` 의 `MotorCalibration` 을 설계하면서. 한계를 어느 자료형에 둘지 정하다가
**결론: cal 공간.** `motors/base.py` 의 `Motor.limits_deg` 로 확정함.
설정 파일 반영은 4~5단계에 남음.

### 두 공간

raw 는 모터가 CAN 으로 보고하는 각도임. 기준점은 그 모터의 기계 영점이고, 그건
사람이 `0xFE` 를 누른 그 순간의 자세임.

cal 은 사람과 기구학이 말하는 관절 각도임. 기준점은 우리가 정한 자세임.

    cal = sign * raw + offset

어긋나는 원인은 둘임.

**기준 자세가 다름 (`offset`)** — 다리가 무거워 `0xFE` 를 정확히 편 자세에서 누를
수 없음. 무릎을 12도 굽은 상태에서 영점 잡으면:

| 물리적 자세 | raw | cal |
|---|---|---|
| 완전히 편 상태 | -12 | 0 |
| 12도 굽힘 (영점 잡은 자세) | 0 | 12 |
| 하드스톱 | 62.79 | 74.79 |

**회전 방향이 다름 (`sign`)** — 양다리는 거울상이라, 같은 굽힘에 대해 한쪽은 CW
한쪽은 CCW 로 돔.

| 물리적 자세 | 오른 무릎 raw | 왼 무릎 raw | cal (양쪽 동일) |
|---|---|---|---|
| 편 상태 | 0 | 0 | 0 |
| 45도 굽힘 | +45 | -45 | 45 |

이것이 cal 공간이 존재하는 이유임. 보행 궤적이 "무릎 45도" 라고 하면 양다리가 같은
동작을 함. raw 로 말하면 다리마다 부호를 뒤집어야 하고, 그걸 잊는 자리가 코드
곳곳에 생김.

감속비 항은 없음 — RobStride 는 출력축 각도를 보고하므로 배율이 필요 없음.

### 무엇이 문제였나

한계값을 raw 로 볼지 cal 로 볼지 정해지지 않아, 비교하는 쪽마다 다른 공간의 값을
맞대고 있었음. 현재 12개 모터 전부 미실측이라 `sign=1, offset=0` 이고, 따라서
`cal == raw` 로 두 공간이 같은 숫자임. **어느 쪽으로 해석해도 지금은 똑같이
동작하므로 드러나지 않음.** 5단계에서 실측값을 넣는 순간 갈라짐.

### 두 자리 중 하나를 골라야 했음

한계를 **재는 값**으로 보면 캘리브레이션에 raw 로 두는 것이 자연스러움 — 관절을
끝까지 훑는 절차에서 `offset` 과 `range` 가 같이 나오므로 한쪽만 갱신하는 것이
불가능해짐.

**본 프로젝트에서는 그 절차가 성립하지 않음.**

| | 손으로 훑을 수 있나 |
|---|---|
| 가벼운 탁상 팔 | 됨 |
| 휴머노이드 다리 | **중력·감속비 때문에 안 됨** |
| 하드스톱까지 밀기 | **그게 피하려는 사고임** |
| 발목 | **두 모터 폐루프. 한쪽만 훑으면 링크가 물림** |

발목이 결정적임. `a1` 을 혼자 끝까지 돌리면 링크가 물리므로 **두 모터를 따로 훑는
절차 자체가 없음.**

따라서 한계는 훑어서 얻는 값이 아니라 **설계에서 오는 값**이고, 첫 동작 전에 이미
알고 있어야 함. 설계값은 영점을 어디에 잡았는지와 무관하므로 cal 공간임.

    훑어서 얻으면   offset 과 한 몸  ->  raw
    설계에서 오면   offset 과 무관   ->  cal

하드스톱은 쇳덩어리라 움직이지 않는데, raw 로 적으면 영점을 다시 잡을 때마다 숫자가
바뀜. 영점을 3도 다른 자세에서 다시 잡으면 무릎 하드스톱의 raw 는 62.79 에서 59.79
가 되지만 cal 은 74.79 로 그대로임.

### 조치

`Motor.limits_deg` (cal 공간, `Optional`) 로 확정함. `MotorCalibration` 은 실측값
(`sign`/`offset`/`zero_reference`) 만 담음.

`lo < hi` 를 `__post_init__` 에서 검사함. cal 공간에는 `sign` 이 개입하지 않아 순서가
뒤집히지 않으므로, 변환할 때마다 `min/max` 로 재정렬할 필요가 없어짐.

`None` 은 "제한 없음" 이 아니라 "아직 모름" 임. `Motor.is_configured` 가 False 가
되어 상위에서 제어 진입을 막음.

**남은 작업 (4~5단계)**

    config/calibration/*.json   limit_lo_deg / limit_hi_deg 제거
    config/robot.yaml           모터별 limits 추가 (cal 공간)
    config/robot.yaml           헤더 주석 수정 -- 현재 "실측값(... limits ...)은
                                calibration/*.json 에 있다" 로 되어 있음

### 함께 정해진 것 — 안전 검사를 정규화에 얹지 않음

한계 검사를 좌표 정규화에 얹으면(정규화 좌표를 `[-100, 100]` 으로 자르면 raw 가
자동으로 범위 안에 들어옴) 한계를 넘는 명령을 만들 방법 자체가 없어짐. 우아하지만
**도(度) 단위를 쓰는 순간 그 보호가 사라짐** — 자를 기준이 없어짐.

본 프로젝트는 도 단위를 씀. 관절 각도를 사람과 궤적이 그대로 쓰기 때문임.

그래서 `safety/guards.py` 를 **명시적인 별도 관문**으로 둠. NaN 검사도 여기 있음 —
정규화에는 NaN 을 거를 자리가 없음.

## 🟢 #3 — `calibrate()` 와 `is_calibrated` 가 `Robot` 계약에 있음


**어디서**: `robots/base.py` 의 `Robot` 계약을 정하면서
**해결됨** — `robots/base.py` 의 `Robot` ABC 에 둘 다 추상 멤버로 넣음.

### 왜 계약에 있어야 하나

각 로봇이 제멋대로 판정하면 호출부가 **"이 로봇은 준비됐나" 를 물어볼 공통 방법이
없어짐.** 미실측 상태로 토크를 넣는 것이 가장 위험한데, 그걸 막는 판정이 구현마다
다르면 막히지 않는 구현이 하나쯤 생김.

`Leg` 만 이 판정을 가지면 `Humanoid` 나 `Arm` 이 생길 때 각자 다시 만들게 되고,
호출부는 타입을 보고 분기해야 함.

### 지금 구조

    Robot.is_calibrated     추상 프로퍼티
    Robot.calibrate()       추상 메서드

`Leg` 의 구현은 **둘 다** 봄.

    config.is_configured            한계와 게인이 채워졌는지
    not unmeasured(calibration)     영점 메모가 남아 있는지

게인만 있으면 어디까지 가도 되는지 모르고, 한계만 있으면 토크가 안 나감.

`Leg.enable()` 이 이 판정을 보고 거부함. 커미셔닝 단계에서는
`allow_uncalibrated=True` 로 만들면 경고만 하고 진행함 -- 실측 전에도 움직여야
실측을 할 수 있기 때문임.

`calibrate()` 는 파일을 다시 읽는 것까지만 함. 재는 절차 자체는 사람이
`scripts/commission.py` 로 함.

## 🟢 #4 — 관측이 제어 경로와 같이 감


**어디서**: `telemetry/` 를 만들면서. 어느 경로에서 부르든 같은 값이 나와야 한다는 것을 정리하다가
**해결됨** — `control/loop.py` 가 매 주기 기록하고, `scripts/bringup.py` 의 움직이는
항목이 전부 그 루프를 탐.

### 무엇이었나

관측 경로가 제어 경로와 따로 놀면, 사람이 손으로 움직여 볼 때는 그래프가 안 나오고
자동 제어 때만 나옴. **게인을 튜닝하려면 손으로 움직이면서 봐야 함.**

메뉴가 로봇을 직접 부르면 그 경로에서만 다음이 빠짐.

    텔레메트리 (UDP·CSV)
    주기 측정 (loop_dt, overruns, kept_up)
    정지 순서 (hold 후 토크 차단)

그러면 그래프가 안 나오는데 **텔레메트리가 고장난 줄 알게 되고**, 같은 일을 하는
코드가 두 벌이 되어 한쪽만 고쳐짐.

### 지금 구조

    menu -> motion -> ControlLoop -> Leg -> bus

메뉴 항목은 `Motion` 만 정하고 `_run()` 에 넘김. `_run()` 이 모드를 CONTROL 로
바꾸고 루프를 돌린 뒤 관찰 모드로 되돌림.

`snapshot.build()` 는 `Robot` 계약만 쓰므로 어느 경로에서 부르든 같은 값이 나옴.

### 고정한 것

`tests/test_bringup.py` 의 `TestGoesThroughTheLoop` 가 `ControlLoop.run` 을 감시함.
움직이는 항목이 루프를 타지 않으면 실패함.

### 예외

되돌리기 어려운 조작(영점, CAN id, 프로토콜)은 `scripts/commission.py` 에 있고
루프를 타지 않음. **반복하지 않는 조작이라 주기가 없음.**

## 🟢 #5 — 종류·개체·기하를 나눔


**어디서**: `config/schema.py` 의 `LimbConfig` 를 설계하면서. 팔이 붙으면 무엇이 달라지는지 따져 보다가
**해결됨** — `config/schema.py` 의 `LimbConfig` 가 셋을 따로 가짐.

### 무엇이었나

값 하나가 세 가지를 겸하면 확장할 때 막힘.

    종류   어떤 기구학을 쓰는지        다리냐 팔이냐
    개체   이 로봇에서 부르는 이름     같은 종류가 둘 이상일 때 구분
    기하   거울상인지                  좌우 대칭 여부

허리처럼 좌우가 없는 부위가 생기면 "왼쪽도 오른쪽도 아님" 을 표현할 수 없음.

### 지금 구조

    limbs:
      right_leg:        <- 개체 이름. 사전의 키
        kind: leg       <- 종류
        side: right     <- 기하. 없어도 됨

개체 이름을 키로 둔 것은 같은 이름이 둘일 수 없게 하려는 것임.

`side` 는 "거울상이다" 라는 사실만 적음. **실제 부호 뒤집기는 캘리브레이션의
`sign` 이 함** -- 그건 재서 얻는 값이라 설정에 올 수 없음. 발목 링키지의 거울상은
`AnkleGeometry.mirrored()` 가 따로 다룸.

`RobotConfig.limbs_of_kind("leg")` 로 종류별로 골라낼 수 있음. 팔이 붙어도 그대로
동작함.

## 🟢 #6 — 컨텍스트 매니저


**어디서**: `motors/canbus.py` 를 쓰면서. 제어 중 예외가 나면 무엇이 남는지 따져 보다가
**해결됨** — 세 계층 전부에 있음.

    CanBus       __enter__ / __exit__
    MotorsBus    ABC 에 기본 구현
    Robot        ABC 에 기본 구현

### 왜 필요한가

제어 중 예외가 나면 **모터가 마지막 명령을 계속 유지함.** 명령을 갱신하는 코드가
죽었으므로 사람이 전원을 뽑을 때까지 다리가 힘을 주고 있음.

    with leg:
        leg.enable()
        raise RuntimeError(...)     # 여기서 터져도 토크가 끊김

### 정리 순서

`RobStrideBus.disconnect()` 가 **토크를 먼저 끊고** 채널을 닫음. 순서가 반대면
채널이 닫힌 뒤라 정지 명령을 보낼 방법이 없어짐.

    left_leg.send(left)                              # 전송을 몰아서

    left_leg.collect()                               # 그 다음에 수거
    right_leg.collect()

다리 하나뿐이면 `send_action()` 하나로 충분함 -- 셋을 순서대로 부름.

## 🟢 #14 — 한계 여유의 방향

**어디서**: `safety/limits.py` 를 쓰면서. 여유를 어느 쪽으로 두는지 정하다가

### 무엇

`limits_deg` 는 **하드스톱 그 자체**임. 여유를 이미 뺀 값이 아님.

따라서 여유는 **안쪽으로** 좁혀야 함.

```python
def safe_window(limits, margin_deg):
    lo, hi = limits
    m = abs(margin_deg)
    return lo + m, hi - m        # 안으로
```

바깥으로 더하면 한계 밖 몇 도까지 허용하게 되어, 여유가 **보호가 아니라 확장**이 됨.

### 여유가 왜 필요한가

세 가지를 흡수함.

```
오버슛     명령이 한계에 딱 붙어 있으면 지나침
관성       무거운 다리는 목표에서 바로 멈추지 않음
측정오차   위치 해상도가 0.022도이고 캘리브레이션 오차도 있음
```

지금 3도는 임의로 잡은 출발점임. **게인을 튜닝하면 필요한 값이 달라짐** — 오버슛이
줄면 여유도 줄일 수 있음.

## 🟢 #15 — 한계를 넘는 명령을 자름

### 버리는 경우도 있음

## 🟢 #16 — MIT 과 private 의 속도 범위가 다름

**어디서**: `motors/robstride/tables.py` 에 인코딩 범위를 옮기면서

### 무엇

같은 RS02 라도 프로토콜에 따라 속도 범위가 다름.

| 조합 | 위치 | 속도 | 토크 | 매뉴얼 |
|---|---|---|---|---|
| RS02 / MIT | ±12.57 rad | **±33 rad/s** | ±17 N·m | p.37~38 |
| RS02 / private | ±12.57 rad | **±44 rad/s** | ±17 N·m | p.20~21 |

무부하 410rpm ≈ 43 rad/s 이므로 private 은 전 범위를, MIT 은 12bit 라 ±33 으로
잘라 쓰는 것으로 보임.

### 왜 중요한가

**틀리면 속도 읽기가 44/33 = 1.33배 어긋남.** 위치와 토크는 영향 없어서 눈에 잘
안 띔.

```python
u = float_to_uint(10.0, -33.0, 33.0, 12)
uint_to_float(u, -33.0, 33.0, 12)     # 10.0   맞음
uint_to_float(u, -44.0, 44.0, 12)     # 13.33  1.33배
```

### 조치

인코딩 표를 `[프로토콜][모델]` 로 인덱싱함. "모델별 사양" 하나로 뭉치면 private
값을 MIT 에 가져다 쓰는 실수가 남.

**없는 조합에 `KeyError` 를 던짐.** 조용히 기본값으로 때우지 않음 — 범위가 틀리면
명령한 값과 실제가 배율만큼 어긋나는데, 실물에서 찾기 매우 어려움.

현재 MIT 만 쓰지만 `PRIVATE_ENCODING` 도 표에 남김. **두 범위가 다르다는 사실
자체가 중요함.**
