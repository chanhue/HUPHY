# 구현 기록 — 무엇을 어떤 순서로, 왜 그렇게

`src/huphy/` 를 만든 순서와 각 단계에서 무엇에 중점을 뒀는지.

**순서에는 이유가 있음.** 아래 계층이 없으면 위 계층을 시험할 수 없고, 관측이
없으면 게인을 찾을 수 없음.

계층 사이의 관계는 [architecture.md](architecture.md), 사용법은
[루트 README](../README.md).

---

## 순서를 정한 원칙

**① 하드웨어 없이 되는 것부터**

로봇을 만질 수 있는 시간은 짧고, 만지는 동안은 코드를 고치기 어려움. 계산이 맞는지를
책상에서 확정해 두면 실물에서는 배선·프로토콜·기하만 보면 됨.

**② 위험한 것을 먼저**

안전 검사를 나중에 붙이면 그 전까지 위험한 상태로 시험하게 됨. 첫 명령이 나가기
전에 관문이 서 있어야 함.

**③ 관측이 제어보다 먼저**

게인을 튜닝하려면 목표와 실측을 겹쳐 봐야 함. 그래프가 없으면 게인을 찾을 수 없고,
게인이 없으면 다리가 안 움직임.

**④ 진입점은 필요해질 때**

커미셔닝 진입점은 설정 읽기 뒤로 당겨졌음 — 실행하려면 모터 목록을 읽어야 했음.
`bringup` 은 제어 루프와 텔레메트리가 다 있어야 해서 마지막에 감.

## 1단계 — 안전

```
safety/limits.py    한계와의 관계 계산
safety/guards.py    명령의 최종 관문
```

**중점: 조용한 실패를 막는 것.**

첫 관문이 유한값 검사인 이유가 여기 있음. 파이썬의 `min`/`max` 는 NaN 을 비교할 수
없어 **그냥 통과시킴.**

```python
min(10, nan)                             # 10       nan < 10 이 False
float_to_uint(nan, -12.57, 12.57, 16)    # 65535 = 720도
```

**NaN 하나가 720도 목표 명령이 됨.** 조용히, 에러 없이. 그래서 인코딩 단계의
클램프에 기댈 수 없고 그 위에서 걸러야 함.

### 버리지 않고 자름

명령을 버리면 그 모터만 직전 명령을 유지해 다리 자세가 어긋남. 발목처럼 두 모터가
연동된 곳에서 특히 나쁨.

자른 것은 반드시 세어 내보냄 — **클리핑은 조용한 변조**이기 때문임. 명령한 것과
다른 게 실행되는데 아무도 모르면 안 됨.

### 자르는 순서

한계를 먼저, 점프를 나중에. 역순이면 중간에 한계 밖 값을 만들고, 실제로는 걸릴
필요가 없는 점프 클리핑이 카운터에 남음.

## 2단계 — 벤더 사양

```
robstride/tables.py       데이터시트에서 오는 값
robstride/codec/mit.py    숫자 ↔ 8바이트
```

**중점: 사양을 코드가 아니라 데이터로 두는 것.**

### 인코딩 범위를 "프로토콜 × 모델" 로 둠

같은 RS02 라도 MIT 은 ±33 rad/s, private 은 ±44 rad/s. 이 축이 없으면 private 값을
MIT 에 가져다 쓰는 실수가 남 — 틀리면 속도 읽기가 1.33배 어긋남.

없는 조합에 `KeyError` 를 던짐. 조용히 기본값으로 때우면 명령한 값과 실제가 배율만큼
어긋나는데, 실물에서 찾기 매우 어려움.

### 라디안 변환을 한 파일에 가둠

내부는 rad, 외부는 deg. 변환이 `codec/mit.py` 에서만 일어나므로 나머지 코드는
라디안을 신경 쓰지 않아도 됨.

### 여기서 NaN 위험을 확인함

`float_to_uint` 가 NaN 을 통과시키는 것을 테스트로 고정함. "코덱이 알아서
막겠지" 라는 오해를 막으려는 것임.

## 3단계 — 통신

```
motors/base.py         벤더 중립 자료형
motors/canbus.py       CAN 전송
robstride/bus.py       런타임 조작
```

**중점: `python-can` 을 한 파일에 가두는 것.**

`canbus.py` 만 `python-can` 을 import 하고, 그것도 함수 안에서 함. 위 계층은
`CanFrame` 만 다룸. 그래서 나머지 전부가 하드웨어 없이 시험됨.

### 적는 것과 재는 것을 나눔

```
Motor              사람이 적는 것    id, model, limits, gains
MotorCalibration   조립을 재는 것    sign, offset, zero_reference
```

무효화 시점이 다름. 모터를 다시 달면 캘리브레이션만 무효가 되고, 기구 설계가
바뀌면 `Motor` 만 바뀜.

### 상태는 명령의 응답으로 옴

MIT 모드에는 **읽기 전용 명령이 없음.** 모터는 동작 명령을 받으면 응답으로 현재
상태를 돌려줌. 그래서 움직이지 않고 상태만 보려면 게인과 토크가 0인 명령을 보냄.

이 사실이 뒤에 여러 곳에 영향을 줌 — 관찰 모드도 통신을 해야 하고, 응답 유무가
곧 명령이 처리됐다는 증거가 됨.

### 전송과 수거를 나눔

`recv()` 는 큐가 비면 타임아웃만큼 블로킹함. 순차로 수거하면 그 시간이 버스 수만큼
곱해짐. 버스가 둘일 때 "전송을 몰고 그 다음 수거" 순서를 짜려면 나뉘어 있어야 함.

### 여기서 정한 것

**한계값을 cal 공간에 둠** ([이슈 #2](issues.md)). 설계에서 오는 값이라 영점을
어디에 잡았는지와 무관함. raw 에 두면 영점을 다시 잡을 때 숫자는 그대로인데
가리키는 물리적 위치가 달라짐.

## 4단계 — 커미셔닝

```
robstride/commissioning.py    조립할 때 한 번 하는 조작
```

**중점: 되돌리기 어려운 것을 제어 경로에서 떼어내는 것.**

영점·CAN id·프로토콜 전환은 `MotorsBus` 계약에 없음. **제어 코드에서 부를 방법
자체가 없음.**

### 이 파일의 절반은 거부 조건임

| 거부 | 왜 |
|---|---|
| 영점 메모 없이 | 모터는 값을 저장하지만 "그때 어떤 자세였는지" 는 안 남음 |
| 토크 켜진 채 영점 | 좌표계가 옮겨가는데 직전 목표각은 옛 좌표계 값임 |
| 쓰는 CAN id 로 변경 | 같은 id 가 둘이면 응답이 충돌해 구분조차 안 됨 |
| 20도 넘는 `nudge` | 확인용이지 동작용이 아님 |

### 한 모터씩만 처리함

여러 개를 연속으로 바꾸다 중간에 실패하면 어느 것이 옛 상태이고 어느 것이 새
상태인지 알 수 없음.

### 여기서 알게 된 것

**파라미터 읽기·쓰기를 할 수 없음** ([이슈 #11](issues.md)). `0x201F`(프로토콜)와
`0x7029`(`zero_sta`)는 29-bit 확장 프레임으로 접근하는데 이 코드는 11-bit 표준
프레임만 보냄.

즉 **하드웨어 전제를 코드로 확인할 수 없음.**

## 5단계 — 설정·실측값·커미셔닝 진입점

```
config/schema.py      설정 자료형
config/loader.py      robot.yaml 읽기
calibration/store.py  실측값 읽기·쓰기
scripts/commission.py 터미널 진입점
```

**중점: 잘못된 설정이 조용히 넘어가지 않게 하는 것.**

### 오타를 읽는 순간 잡음

YAML 은 모르는 키를 조용히 넘김.

```
contorl_hz: 200     ->  무시되고 기본값 100Hz 로 돎
```

**설정을 고쳤는데 아무것도 안 바뀜.** 증상이 "느리다" 로 나타나므로 원인을
설정에서 찾을 이유가 없어 오래 걸림.

### 기본값을 스키마에만 둠

`loader` 는 YAML 에 있는 키만 골라 넘김. 없는 키는 아예 안 넘겨서 dataclass 의
기본값이 쓰임. 두 군데 있으면 어느 쪽이 실제로 쓰이는지 알 수 없음.

### 스키마가 스스로 검사함

`__post_init__` 에서 검사하므로 **파일에서 읽든 코드로 만들든 같은 검사를 받음.**
`loader` 에만 두면 테스트에서 손으로 만든 설정은 그냥 통과함.

### 저장이 원본을 지킴

실측값은 임시 파일에 쓰고 바꿔치기함. 도중에 죽으면 원본이 그대로 남음 — 실측값을
잃으면 다시 재는 수밖에 없는데, 그건 로봇을 분해해야 하는 작업일 수 있음.

### 순서를 바꾼 곳

커미셔닝 진입점이 여기로 당겨졌음. 4단계에서 함수는 만들었지만 **실행할 방법이
없었고**, 실행하려면 설정 파일에서 모터 목록을 읽어야 했음.

```
4단계 커미셔닝  ->  5단계 설정  ->  진입점  ->  실물 확인
```

### 여기서 정리된 것

이름·종류·기하를 나눔 ([이슈 #5](issues.md)). `limbs` 의 키가 개체 이름,
`kind` 가 종류, `side` 가 기하. 하나가 셋을 겸하면 팔이나 허리가 붙을 때 막힘.

## 6단계 — 기구학과 로봇

```
kinematics/ankle.py   발목 2모터 링키지
robots/base.py        Robot 계약
robots/leg.py         다리 하나
```

**중점: 경계를 한 곳에 모으는 것.**

### 발목만 기구학이 필요함

다른 관절은 모터 하나가 관절 하나를 돌리므로 변환할 것이 없음. 발목은 모터 두 개가
로드 두 개로 발판 하나를 밀고 당김.

### 두 각도를 같은 규약으로

모터가 `zero_sta=1` 로 `[-180,180)` 을 보고함. 한쪽만 `[0,360)` 이면 IK 가 340도를
돌려주고 모터는 -20도를 보고해 **360도 차이**가 남 ([이슈 #1](issues.md)).

### 여기서 알게 된 것

**FK 는 답이 하나가 아님.** 같은 모터각 조합이 서로 다른 자세 둘에 대응함.
링키지의 성질이지 버그가 아님.

```
IK(90, 90)  ->  (52.10, 45.41)
FK(52.10, 45.41)  추정 (0,0)    ->  (2.41, -40.48)
FK(52.10, 45.41)  추정 (90,90)  ->  (90.00,  90.00)
```

시험 범위 안에서는 추정 `(0,0)` 으로도 항상 원래 자세를 찾음 — 격자 187개로
확인함. 범위를 넓히면 다시 봐야 함.

**거울상은 좌표만 뒤집으면 안 됨.** `crank_t` 는 x 방향 오프셋이고 모터 회전축이
x 축이라 부호도 같이 뒤집혀야 함. 그래야
`왼(pitch, -roll) = -오른(pitch, roll)` 이 정확히 성립하고, 보행 궤적 한 벌로
양다리를 움직일 수 있음.

### 경계에서 일어나는 네 가지

관절 이름 → 모터 id, cal → raw, 발목 IK, 안전 검사. **넷 다 `robots/` 에서만**
일어남.

**검사가 변환보다 먼저임.** raw 로 내린 뒤 검사하면 `sign` 이 -1 인 관절에서 부호가
뒤집혀 한계가 반대로 걸림.

### 발목의 두 실패를 다르게 다룸

| | 어떻게 |
|---|---|
| IK 가 안 풀림 | **통째로 버림.** 한쪽만 보내면 로드 둘이 다른 자세를 요구해 비틀림 |
| 한계에 잘림 | 개별 처리. 잘린 각도 쌍도 대응하는 발 자세가 있음 |

실제로 실행된 자세는 FK 로 되짚어 냄 — 무엇을 보냈는지가 아니라 **무엇이
실행됐는지**를 기록해야 로그를 믿을 수 있음.

## 7단계 — 관측

```
telemetry/snapshot.py   필드 이름을 정하는 유일한 곳
telemetry/udp.py        실시간
telemetry/csv_log.py    기록
```

**중점: 제어를 방해하지 않으면서 무슨 일이 있었는지 남기는 것.**

제어보다 먼저 만든 이유는 순서 원칙 ③ 그대로임.

### 필드 이름을 한 곳에서만

UDP 와 CSV 가 같은 사전을 소비함. 두 군데에서 만들면 CSV 헤더에는 있는데 UDP 에는
없는 값이 생기고, 어느 쪽이 맞는지 알 수 없어짐.

`field_names()` 가 **실행 전에** 목록을 냄 — CSV 헤더를 첫 줄에 써야 함.

### 예외를 던지지 않음

네트워크가 끊기거나 디스크가 차는 것은 로봇 입장에서 정상 상황임. 실패는 세기만
하고 처음 한 번만 로그를 남김.

**관측이 제어를 멈추면 관측할 대상이 없어짐.**

### `tgt` 는 실제로 나간 명령임

명령한 값을 기록하면 **한계에 걸린 것과 게인이 낮은 것이 그래프에서 구분되지
않음.**

### 여기서 추가한 것 — 명령이 씹혔는지

`ack` 가 두 층임을 정리함.

```
CAN 하드웨어 ACK    버스의 아무 노드나 찍어줌. "누군가 들었다"
응답 프레임         그 모터가 처리했다는 증거
```

`tx_errors` 와 같이 보면 원인이 좁혀짐.

| `tx_errors` | `ack` | 뜻 |
|---|---|---|
| 0 | 1 | 정상 |
| 0 | 0 | **모터가 명령을 무시함** — 프로토콜·모드 불일치 |
| > 0 | — | 버스에 아무도 없음 — 배선·전원 |

**`age` 가 가장 믿을 만함.** 응답이 한 번도 없던 모터는 위치를 몰라 가드가 명령을
거부하고, 명령이 안 나갔으니 응답 대상에서도 빠져 `ack` 가 `-1` 로 가려짐.

### 패킷을 둘로 나눔

한 다리가 필드 66개면 약 1.8 KB 로 MTU(1500)를 넘어 조각남. **조각 하나만 잃어도
패킷 전체가 버려짐.**

```
빠른 것  매 주기      32필드  850 B   pos tgt err vel tau
진단     10주기마다   35필드  950 B   temp age ack miss, 카운터
```

나누는 것이 자연스럽기도 함 — `temp` 는 초 단위로 변하고 카운터는 사건이 있을
때만 변함.

CSV 는 안 나눔. 크기 제약이 없고 한 줄에 다 있어야 대조하기 쉬움.

## 8단계 — 제어

```
control/loop.py      주기와 안전
control/motions.py   무엇을 시킬지
```

**중점: 주기를 정직하게 재는 것.**

### 루프와 동작을 나눔

루프는 주기와 안전만 봄. 무엇을 시킬지는 동작이 정함. 같은 루프로 유지·계단·
사인파·보행 궤적을 다 돌릴 수 있고, 동작은 순수 함수라 하드웨어 없이 시험됨.

### 주기를 두 가지로 잼

```
overruns   튀는 주기.     목표의 1.5배를 넘긴 횟수
kept_up    꾸준한 느림.   평균이 목표의 90% 미만
```

**둘이 다름.** 매 주기 24%씩 넘으면 한 번도 "밀림" 으로 세지 않으면서 주파수만
떨어짐.

주기가 밀리는데 게인을 튜닝하면 게인이 아니라 주기가 문제인데 게인을 계속 만지게 됨.
그래서 끝날 때 경고함.

### 마감 직전은 자지 않고 기다림

`time.sleep` 은 요청한 만큼 정확히 자지 않음. 100Hz 에서 84.7Hz 가 나왔음.

```
남은 시간 > 3ms   ->  (남은 시간 - 3ms) 만큼 잠
남은 시간 <= 3ms  ->  돌면서 마감을 봄
```

여유가 잠의 오차보다 커야 함 — 작으면 한 번의 긴 잠이 마감을 지나쳐 버려 스핀할
구간이 없어짐. 재보니 오차가 약 1.9ms 라 3ms 로 잡음.

| 목표 | 끄면 | 켜면 |
|---|---|---|
| 100Hz | 84.7Hz | **99.9Hz** |
| 200Hz | 164.1Hz | **200.0Hz** |

### 관찰 모드도 통신을 함

MIT 프로토콜에는 읽기 전용 명령이 없음. 아무것도 보내지 않으면 아무것도 오지 않음.
힘이 나가지 않는 명령을 보내고 그 응답을 받음.

토크를 끊고 시작하는 것은 **하드 안전장치**임 — 설정이 잘못돼 있어도 다리가 안
움직이게 함.

### 멈출 때 자세를 먼저 붙잡음

서 있는 다리에서 힘이 갑자기 빠지면 주저앉음. 끝나는 경로가 하나라 정상 종료든
예외든 같은 순서를 탐.

## 9단계 — 브링업 메뉴

```
scripts/bringup.py   다리를 실제로 움직여 보는 대화형 메뉴
```

**중점: 메뉴가 제어 루프를 타게 하는 것** ([이슈 #4](issues.md)).

```
menu -> motion -> ControlLoop -> Leg -> bus
```

메뉴가 로봇을 직접 부르면 그 경로에서만 텔레메트리·주기 측정·정지 순서가 빠짐.
그러면 **그래프가 안 나오는데 텔레메트리가 고장난 줄 알게 되고**, 같은 일을 하는
코드가 두 벌이 되어 한쪽만 고쳐짐.

메뉴는 `Motion` 만 정하고 넘김. 테스트가 `ControlLoop.run` 을 감시해 고정함.

### 모든 동작이 `freeze` 로 시작함

지금 자세를 잡고 거기서 출발함. 목표를 0으로 잡고 시작하면 **토크를 넣는 순간
다리가 0을 향해 한 번에 움직임.**

흔들지 않는 관절은 지금 자리에 붙잡아 둠 — 여럿을 같이 흔들면 어느 관절이 원인인지
섞임.

### 한계 밖에 있으면 경고함

관절이 한계 밖에 있으면 토크를 넣는 순간 가드가 한계 안으로 끌어당김. **그 방향으로
움직이므로** 사람이 알고 있어야 함.

## 하지 말 것

만들면서 실제로 겪은 것들.

| | 왜 |
|---|---|
| 테스트 없이 다음 계층으로 | 실물에서 디버깅하면 훨씬 비쌈 |

| 미실측 값을 그럴듯하게 채우기 | 튜닝된 것처럼 보여 그대로 실행하게 됨 |
| 같은 값을 두 파일에 | 한쪽만 고쳐짐 |
| 같은 검사를 두 계층에 | 어느 쪽이 맞는지 알 수 없음 |
