# 모니터링 — 무엇을 왜 보는가

게인을 튜닝하고 사고를 조사하기 위해 무엇을 내보내는지. 구현은
[`telemetry/README.md`](../src/huphy/telemetry/README.md).

---

## 1. 왜 필요한가

**게인을 튜닝하려면 목표와 실측을 겹쳐 봐야 함.**

```
목표를 지나쳤다 돌아옴    ->  kd 를 올림
목표까지 못 감            ->  kp 를 올림
부르르 떨림               ->  kp 를 내림
```

눈으로만 보면 "지나쳤다 돌아온다" 를 구분할 수 없음. 그래프가 없으면 게인을 찾을
수 없고, 게인이 없으면 다리가 안 움직임.

그래서 제어보다 먼저 만들었음.

**두 번째 이유는 사고 조사임.** 뭔가 잘못됐을 때 그 직전 몇 초를 프레임 단위로
다시 볼 수 있어야 함.

---

## 2. 도구 — PlotJuggler

| 필요한 것 | PlotJuggler |
|---|---|
| 실시간 스트리밍 | UDP 서버 내장 |
| JSON 파싱 | 내장 |
| 여러 신호 겹쳐 보기 | 됨 |
| 시간축 지정 | `t` 를 timestamp 로 지정 |
| 수치와 그래프 동시 | 커서를 올리면 값이 보임 |
| CSV 로 되돌아보기 | 같은 도구로 열림 |

같은 도구로 **실시간과 기록을 다 봄.** 튜닝 중에는 스트리밍, 나중에는 CSV.

---

## 3. 구조

```
라즈베리파이                          우분투 (또는 같은 네트워크의 PC)
──────────────                       ────────────────────────────
control/loop.py
   │ 매 주기
telemetry.record()
   ├─ UDP ──────── 로컬 네트워크 ──────> PlotJuggler
   └─ CSV
      logs/*.csv                        (나중에 열어 봄)
```

**인터넷은 필요 없음.** 파이와 PC 가 서로 닿는 로컬 네트워크면 됨.

| 연결 | |
|---|---|
| 같은 공유기 | 가장 간단 |
| 랜선 직결 (정적 IP) | 지터가 가장 작음 |

```bash
sudo ufw allow 9870/udp                       # 받는 쪽
ping <파이 IP>
echo '{"t":1,"x":42}' | nc -u -w1 <PC IP> 9870   # 확인
```

## 4. 무엇을 보나

### 4.1 추종 성능 — 튜닝의 주 화면

```
right_leg/knee/pos    실측 위치 (cal 공간)
right_leg/knee/tgt    목표 위치. 실제로 나간 것
right_leg/knee/err    tgt - pos
right_leg/knee/vel    실측 속도
```

**`pos` 와 `tgt` 를 겹쳐 놓는 것이 전부임.**

| 그래프 | 뜻 | 할 것 |
|---|---|---|
| 목표까지 못 감 | `kp` 부족 | `kp` 올림 |
| 지나쳤다 돌아옴 | `kd` 부족 | `kd` 올림 |
| 부르르 떨림 | `kp` 과함 | `kp` 내림 |
| 느리게 도달 | 여유 있음 | `kp` 올릴 수 있음 |

`vel` 은 진동을 먼저 보여줌 — 위치가 흔들리기 전에 속도가 먼저 요동침.

#### `tgt` 는 명령한 값이 아님

**실제로 나간 값**임 (`robot.last_sent`). 한계나 점프에 걸리면 잘린 뒤의 값임.

명령한 값을 기록하면 **한계에 걸린 것과 게인이 낮은 것이 그래프에서 구분되지
않음.** 둘 다 "목표에 못 미침" 으로 보임.

### 4.2 구동 노력 — 포화 판별

```
right_leg/knee/tau    실측 토크 (N·m)
```

**상한에 붙어 있으면 `kp` 를 올려도 소용없음.**

| 모델 | 상한 |
|---|---|
| RS02 | ±17 N·m |
| RS00 | ±14 N·m |

이미 낼 수 있는 힘을 다 내고 있는 것임. 기구를 바꾸거나 목표를 낮춰야 함.

`tau` 가 계속 큰데 안 움직이면 **뭔가에 걸린 것**임.

### 4.3 열

```
right_leg/knee/temp   권선 온도 (°C)
```

초 단위로 변하므로 진단 패킷에 있음. 130°C 에서 모터가 보호 동작함.

**계속 오르면 과부하임.** 게인이 너무 높거나, 기구에 저항이 있거나, 자세가
중력을 계속 이기고 있는 것.

### 4.4 안전 — 무엇이 잘렸나

```
right_leg/guard/clip_limit       한계에 잘린 횟수 (누적)
right_leg/guard/clip_jump        점프에 잘린 횟수
right_leg/guard/reject_nan       NaN 이라 버린 횟수
right_leg/guard/reject_nostate   현재 위치를 몰라 버린 횟수

since_clip                       마지막 클리핑 이후 경과 (초)
since_reject                     마지막 거부 이후 경과 (초)
```

누적값이라 **계단처럼** 올라감. 평평하면 정상.

`since_*` 는 사건 직후 0으로 떨어졌다 올라가서 **언제 일어났는지가 눈에 바로 띔.**
누적 카운터만으로는 그래프에서 계단을 찾아야 함.

**`reject_nan` 이 하나라도 오르면 계산이 발산한 것.** 발목 IK 나 0으로 나누기가
후보임.

**`clip_jump` 이 계단 응답 때 오르는 것은 정상임.** 점프 가드가 계단을 자르므로
실제로는 몇 주기에 걸쳐 올라감 — 그 기울기가 속도 상한임.

### 4.5 통신 — 명령이 씹혔나

```
right_leg/knee/ack     1 응답함 / 0 씹힘 / -1 명령하지 않음
right_leg/knee/age     마지막 응답 이후 경과 (ms). 한 번도 없었으면 -1
right_leg/knee/miss    연속 무응답 주기 수
missing                명령했는데 응답이 없는 모터 수

right_leg/can/tx_errors        송신 실패
right_leg/can/rx_errors        수신 실패
right_leg/can/drain_timeouts   기대한 응답을 못 채운 횟수
```

**MIT 모드는 명령을 받으면 반드시 답함.** 안 오면 그 모터가 처리하지 않은 것임.

#### 두 카운터를 같이 봐야 원인이 좁혀짐

| `tx_errors` | `ack` | 뜻 |
|---|---|---|
| 0 | 1 | 정상 |
| 0 | 0 | **모터가 명령을 무시함** — 프로토콜·제어 모드 불일치 |
| > 0 | — | 버스에 아무도 없음 — 배선·전원 |

CAN 하드웨어 ACK 는 버스에 붙은 아무 노드나 찍어주므로 "누군가 들었다" 일 뿐임.
모터별로 처리됐는지는 응답 프레임으로만 알 수 있음.

#### `age` 가 가장 믿을 만함

응답이 한 번도 없던 모터는 위치를 몰라 가드가 명령을 거부하고(`reject_nostate`),
명령이 안 나갔으니 응답 대상에서도 빠져 **`ack` 가 `-1` 로 가려짐.**

`age` 는 명령 여부와 무관하게 참임.

```
모터           ack  miss   age(ms)
ankle_a2      -1.0   1.0     -1.00   <- 한 번도 응답 없음
reject_nostate 3.0                    <- 매 주기 거부됨
can/tx_errors  0.0                    <- 배선이 아니라 모터가 무시하는 것
```

### 4.6 루프 — 가장 먼저 볼 것

```
t          시작부터 흐른 초
loop_dt    직전 루프 실제 주기 (ms)
```

**게인을 만지기 전에 이것부터 봄.** 주기가 밀리는데 게인을 튜닝하면 게인이 아니라
주기가 문제인데 게인을 계속 만지게 됨.

100Hz 목표면 `loop_dt` 가 10ms 근처여야 함. 15ms 가 나오면 계산이나 수거가 예산을
넘긴 것.

루프가 끝날 때 요약도 나옴.

```
51주기 0.6초 (평균 84.8Hz / 목표 100Hz), 밀림 0회, 최악 12.5ms,
무응답 주기 5회  ** 주기를 못 지킴 **
```

**`밀림` 과 `주기를 못 지킴` 이 다름.** 매 주기 24%씩 넘으면 한 번도 밀림으로 세지
않으면서 주파수만 떨어짐.

## 5. 전송 포맷

### 평면 JSON, 한 패킷 = 한 시점

```json
{"t":1.5,"loop_dt":10.1,"right_leg/knee/pos":10.2,"right_leg/knee/tgt":12.0, ...}
```

`/` 로 나눔. PlotJuggler 가 트리로 묶어 보여줌 — 모터가 20개를 넘어가면 평평한
목록에서는 찾을 수 없음.

**팔다리 이름이 앞에 붙음.** 양다리를 같이 기록할 때 `knee` 가 둘이 됨.

### 숫자만 보냄

PlotJuggler 는 숫자만 그림. 불리언은 `0`/`1`, "없음" 은 `-1` 로 보냄 — 무한대는
JSON 으로 못 보내고 CSV 에서도 읽기 어려움.

### 패킷을 둘로 나눔

| | 주기 | 필드 | 크기 |
|---|---|---|---|
| 빠른 것 | 매 주기 | `pos tgt err vel tau` | 약 850 B |
| 진단 | 10주기마다 | `temp age ack miss`, 카운터, `since_*` | 약 950 B |

**합치면 66필드 약 1.8 KB 로 이더넷 MTU(1500)를 넘어 조각남.** 조각 하나만 잃어도
패킷 전체가 버려져 손실률이 확 올라감.

나누는 것이 자연스럽기도 함 — `temp` 는 초 단위로 변하고 카운터는 사건이 있을 때만
변함.

**팔다리마다 따로 보냄.** 두 다리를 합치면 또 넘침.

### 반올림

소수점 둘째 자리까지. 패킷 크기를 반으로 줄이는 데 이게 제일 큼.

0.01도는 **모터 해상도(0.022도)보다 촘촘해서 정보를 잃지 않음.**

### 시간축

`t` 를 PlotJuggler 의 timestamp 필드로 지정할 것. 지정하지 않으면 **수신 시각**을
쓰게 되어 네트워크 지터가 데이터에 섞임.

첫 호출을 0으로 하는 상대 시간임. 벽시계를 쓰면 x 축이 `1.7e9` 에서 시작해 읽을 수
없음.

## 6. 필드 이름을 한 곳에서만 정함

`telemetry/snapshot.py` 가 사전 하나를 만들고 **UDP 와 CSV 가 둘 다 그것을
소비함.**

두 군데에서 만들면 CSV 헤더에는 있는데 UDP 에는 없는 값이 생기고, 어느 쪽이 맞는지
알 수 없어짐.

```python
snapshot.field_names(robot)   # 실행 전에 알 수 있음
snapshot.build(robot, t=1.5)  # 그 목록과 정확히 같은 키
```

**실행 전에 알 수 있어야 함** — CSV 헤더를 첫 줄에 써야 하고, PlotJuggler 레이아웃도
미리 만들어 둠.

**필드가 나타났다 사라지면 안 됨.** 값이 없어도 키는 내보내고 `0` 을 채움.

## 7. 관측이 제어를 방해하지 않음

**예외를 던지지 않음.** 네트워크가 끊기거나 상대가 꺼져 있거나 디스크가 차는 것은
로봇 입장에서 정상 상황임. 실패는 세기만 하고 처음 한 번만 로그를 남김.

**UDP 인 이유** — TCP 는 상대가 안 받으면 송신이 막힘. 제어 루프 한가운데서 막히면
주기가 통째로 밀림. 패킷이 몇 개 빠져도 그래프에 점 하나가 비는 것뿐임.

**CSV 는 `flush_every` 주기마다만 디스크에 씀.** 매 줄 쓰면 제어 주기가 튐. 멈출
때는 반드시 밀어 넣음 — 버퍼에 남은 것이 사라지면 하필 사고 직전 몇 줄을 잃음.

**자체 카운터는 UDP 로 안 나감.** 나가는 경로가 고장났는데 그 사실을 같은 경로로
알릴 수는 없음.

## 8. 쓰는 법

```yaml
# config/robot.yaml
telemetry:
  host: 192.168.0.10     # 받는 PC. 비우면 UDP 안 보냄
  port: 9870
  csv_path: logs/leg.csv # 비우면 파일 안 만듦
  csv_flush_every: 50
```

```bash
# 받는 쪽
PlotJuggler -> Streaming -> UDP Server -> Port 9870, JSON -> Start
             timestamp 필드를 t 로 지정

# 파이
python -m huphy.scripts.bringup --limb right_leg
```

## 9. 아직 안 넣은 것

| | 왜 |
|---|---|
| 발목 `pitch`/`roll` 실측 | 모터가 보고하는 값이 아니라 FK 로 푸는 값임. 넣으려면 스냅샷에서 `ankle_pose()` 를 부르면 됨 |
| 한계까지 남은 여유 | `safety.limits.margin_to_limit()` 은 있음 |
| 게인 값 | 설정에 고정이라 실행 중 안 바뀜 |
| 진단 패킷 주기 설정 | 지금은 코드 기본값(10주기) |

발목 관절각은 사람이 보고 싶은 값임 — 지금은 `a1`/`a2` 모터 각도만 보임. 넣는다면
N주기마다 한 번만 FK 를 돌리는 방식이 될 것.
