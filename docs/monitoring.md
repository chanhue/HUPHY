# 실시간 모터 모니터링 설계 (PlotJuggler + UDP)

라즈베리파이의 다리 모터 제어(`single_leg_controller.py`) 상태를, 우분투 PC의
PlotJuggler에서 **실시간으로 시각화**하기 위한 설계 문서.

---

## 1. 목적 (왜 필요한가)

- **게인/영점 튜닝**: `kp/kd`를 바꿀 때 모터가 목표를 어떻게 추종하는지(오버슛,
  진동, 정상상태 오차)를 눈으로 봐야 빠르게 조정할 수 있다.
- **디버깅**: 제어 명령(target)과 실제(pos)의 차이, 토크 급증, E-STOP 원인 등을
  시간축에서 바로 확인.
- **안전**: 한계 근처 접근, 토크 과부하 등을 실시간으로 감지.
- **Sim2Real 검증**: 실물 응답을 로그로 남겨 시뮬레이션과 비교.

즉, "명령을 보냈는데 실제로 어떻게 움직였나"를 **제어 루프를 방해하지 않고** 보는 것.

---

## 2. 도구 선택: 왜 PlotJuggler

| 도구 | 실시간 | 세팅 난이도 | C++ 전환 | 비고 |
|---|---|---|---|---|
| **PlotJuggler** ✅ | 강함 | 낮음(UDP만) | **최적** | 뷰어가 C++/Qt, 전송이 언어무관 |
| Rerun | 강함 | 낮음 | 좋음(C++ SDK) | 3D 등 확장성 좋음 |
| Grafana + InfluxDB | 보통 | 높음(DB 필요) | 보통 | 이력 저장엔 강하나 무겁고 지연 |
| Foxglove + MCAP | 강함 | 중간 | 좋음 | 표준 로그 포맷, 세팅 무거움 |
| matplotlib live | 약함 | 낮음 | ✗ | 루프 타이밍 방해, 느림 |

### 채택 이유 (PlotJuggler)
1. **제어 코드는 UDP로 JSON만 쏘면 끝** → 논블로킹, **실시간 루프 안전**.
2. **전송 규격(UDP telemetry)이 언어 무관** → 지금은 파이썬, 나중에 **C++로
   리팩토링해도 같은 UDP 패킷만 쏘면 뷰어/대시보드는 그대로**. 시각화 재작업 0.
3. **뷰어 쪽 코드 0줄** → 필드를 드래그해서 그래프. DB 불필요.
4. 로봇업계에서 실시간 제어 텔레메트리에 표준적으로 쓰임.

> C++ 마이그레이션을 전제로 하면 "시각화 계층이 언어에 안 묶이는 것"이 핵심 기준이고,
> UDP 전송 규격을 계약(contract)으로 고정하는 PlotJuggler 방식이 여기에 가장 부합한다.

## 3. 시스템 구조

```mermaid
flowchart LR
    subgraph PI["라즈베리파이 (제어)"]
        CTRL["single_leg_controller.py\n(제어 루프 / 메뉴)"]
        TELE["telemetry\n(UDP 송신, 논블로킹)"]
        CTRL -->|"pos/target/vel/tau"| TELE
    end
    subgraph NET["로컬 네트워크 (인터넷 아님)"]
        direction LR
        LINK["UDP :9870\n같은 공유기 or 랜선 직결"]
    end
    subgraph UBU["우분투 (모니터링)"]
        PJ["PlotJuggler\nUDP Server :9870 (JSON)"]
        VIEW["실시간 그래프\n(드래그해서 배치)"]
        PJ --> VIEW
    end
    CAN["CAN 버스\n(RobStride 모터 x6)"] <-->|MIT| CTRL
    TELE -->|"sendto(우분투IP, 9870)"| LINK --> PJ
```

### 텍스트 요약
```
[CAN 모터] <-MIT-> [파이: 제어 + UDP송신] --UDP:9870--> [우분투: PlotJuggler]
                                (로컬 네트워크, 인터넷 불필요)
```

- 제어와 모니터링을 **물리적으로 분리** → 파이는 제어에 집중, 시각화 부하는 우분투가.
- UDP는 **연결(핸드셰이크) 없음** → 파이가 우분투 IP로 쏘기만 하면 됨. 뷰어가 꺼져
  있어도 제어는 영향 없음(패킷만 버려짐).

## 4. 데이터 스펙

### 4.1 무엇을 모니터링할 것인가

모터 제어에서 실시간으로 보는 값은 목적별로 6가지로 나뉜다. 각 신호마다 "이게 없으면
무엇을 못 보는가"를 기준으로 정리한다. 이 이유들이 곧 PlotJuggler 레이아웃을 결정한다.

---

#### (1) 추종 성능 — 튜닝의 주 화면

**목표 위치 `tgt` vs 실측 위치 `pos`**

겹쳐 그리는 것이 위치 제어의 기본 화면. 오버슛·정착시간·상승시간·정상상태 오차가 전부
이 한 장에서 읽힌다.

이 코드에서 특히 중요한 이유가 하나 더 있다. **목표값이 두 종류다** — `set_leg_action`이
저장한 요청값(`action[mid].position_deg`)과, `_build_send_raw_from_joint_error` +
`_resolve_raw_target_near_current`가 360° wrap을 해소한 뒤 **실제로 MIT 프레임에 실린
값**. 모터 펌웨어의 PD가 오차를 계산할 때 쓰는 건 후자다. wrap 로직이 잘못 동작하면
`tgt`가 갑자기 360° 점프하는 것으로 그래프에 드러나는데, 이걸 볼 수 있는 다른 수단이 없다.

> 현재 CSV(`m{id}_target_pos_deg`)는 **요청값**을 기록하고 있어 실제 전송값과 다를 수 있다.
> 텔레메트리는 실제 전송값을 보내야 한다. (→ §4.4)

**위치 오차 `err = tgt − pos`**

파생값인데도 별도 채널로 보내는 이유는 세 가지다.

1. **스케일이 다르다.** 위치는 ±70° 범위인데 오차는 ±2° 범위다. 같은 축에 겹쳐 그리면
   오차 곡선이 직선처럼 눌려 보인다.
2. **숫자로 읽어야 한다.** PlotJuggler 좌측 목록의 값 컬럼에서 정상상태 오차를 바로 읽을
   수 있다. `tgt`와 `pos` 두 숫자를 눈으로 빼면 0.3° 같은 값은 신뢰할 수 없다.
3. **옵션3 진단의 핵심 신호다.** `_step_motor_toward_raw`가 명령을
   `nxt = cur + clamp(goal−cur, ±step_deg)`로 만들기 때문에 오차가 구조적으로
   `step_deg`(2°)를 넘을 수 없다. **`err` 그래프가 2°에서 평평하게 눌리면 그게 "오차 갇힘"의
   직접 증거이고**, 절대 setpoint 램프로 고친 뒤에는 오차가 자유롭게 커지는 것이 보여야 한다.
   즉 수정의 검증 수단이기도 하다. (→ [option3_control_analysis.md](../leg_control/docs/option3_control_analysis.md))

**실측 속도 `vel`**

- **발진 판별**: `err ≈ 0`인데 `vel`이 떨리면 kd 부족.
- **스틱션/걸림 판별**: 명령은 계속 전진하는데 `vel = 0`이면 물리적으로 걸린 것. `err`만
  보면 "아직 도달 못 함"과 구분이 안 된다.
- **디코딩 검증**: PlotJuggler의 미분 변환으로 `pos`를 미분해 `vel`과 겹쳐본다. 두 곡선이
  안 맞으면 `MOTORS[mid].vmax_rad_s`가 틀린 것이다. (RS02 = 44 rad/s, 매뉴얼 p.20 Type 1)
  실물로 교차검증할 수 있는 몇 안 되는 기회다.

#### (2) 구동 노력 — 포화 판별

**실측 토크 `tau`**

- **부하 실측**: 관절 각도에 따라 중력 모멘트가 어떻게 변하는지를 추정이 아니라 실측으로
  얻는다. option3 분석의 "필요 토크(θ)" 논증을 실제 수치로 대체할 수 있다.
- **이상 감지**: 토크 급증 = 충돌·끼임·하드스톱 접촉.

**토크 포화 여부 (RS02 `limit_torque` = 17 N·m)**

`tau`가 상한에 달라붙어 있으면 **게인을 아무리 올려도 소용없다.** 이 구분을 못 하면
포화 상태에서 kp를 계속 올리다가 발진만 만들게 된다 — 튜닝 실패의 대표적 경로다.

근거: 매뉴얼 p.10 파라미터 `0X2007 limit_torque` (Max 17 / 기본 17), p.3 Peak load 17 N·m.

**예상 토크 `kp·err − kd·vel` vs 실측 `tau`** ← 진단력이 가장 높은 조합

MIT 모드에서 PD 계산은 모터 펌웨어가 한다. 파이썬은 `(pos, vel, kp, kd, tau_ff)`만 보낸다:

```
τ = kp·(pos_cmd − pos_meas) + kd·(vel_cmd − vel_meas) + τ_ff
  = kp·err − kd·vel          (vel_cmd = 0, τ_ff = 0인 현재 설정)
```

이 이론값을 계산해 실측 `tau`와 겹쳐 그리면 세 가지가 한 번에 구분된다:

| 그래프 모양 | 해석 |
|---|---|
| 두 곡선 일치 | PD가 예상대로 동작. 모델·게인·부호 전부 맞음 |
| 이론값 > 실측 | 토크 포화 또는 전류 제한에 걸림. 게인 문제 아님 |
| 이론값이 상수에 고정 | **오차 갇힘.** `kp·step_deg`에 묶인 것 (옵션3 문제) |

이 계산에 `kd`가 들어가므로 (3)의 게인 전송이 선택이 아니라 필수가 된다.

#### (3) 제어 파라미터 `kp` / `kd`

**값이 안 바뀌어도 매 패킷 같이 보낸다.**

튜닝 세션은 본질적으로 "게인 바꾸고 → 응답 보고 → 다시 바꾸고"의 반복이다. 게인이 로그에
없으면 **세션 전체가 해석 불가능한 데이터**가 된다. 나중에 로그만 보고 "이 구간은 kp가
얼마였지"를 기억에 의존해야 하는데, 그게 되는 세션은 없다. 흔히 빠뜨리는 항목이다.

또한 (2)의 이론 토크 계산에 직접 들어가므로 없으면 그 그래프를 그릴 수 없다.

이 코드 특유의 주의점 두 가지:

- **게인 소스가 두 곳이다.** `self.gains[mid]`(기본)와 `cmd.kp`/`cmd.kd`(명령별 오버라이드)가
  `_prepare_mit_payload`에서 합쳐진다. 보내야 할 건 **실제 프레임에 실린 값**이다.
- **감쇠 구간에서 덮어써진다.** `_send_damping_all`은 `kp=0`, `kd=DAMPING_KD`(=1.0)로
  강제한다. 그래프에서 kp가 0으로 뚝 떨어지는 순간이 `damping` 플래그와 일치해야 하고,
  이게 서로의 교차검증이 된다.

#### (4) 안전 / 한계

**한계까지 여유 `margin`**

절대 각도로 보면 안 되는 이유: 한계가 모터마다 다르고 **비대칭**이다 (예: m10 knee =
−20.65 ~ 74.79°). 절대각을 보면서 매번 머리로 빼야 한다. `margin`은 음수면 넘은 것이라
0선 하나만 보면 된다.

그리고 이 코드에서 결정적인 용도가 하나 있다. `_is_near_stop()`은 **6개 모터 중 하나라도**
한계 8°(`NEAR_STOP_MARGIN_DEG`) 안에 들어오면 True를 반환하고, 그러면 **다리 전체가**
감쇠 모드로 전환된다. 즉 "왜 갑자기 힘이 빠졌나"의 범인이 어느 모터인지는 **`margin`을
6개 다 봐야만 알 수 있다.** 그래프에 8° 기준선을 그어두면 전환을 예측할 수도 있다.

**`estop` + `estop_code`**

- E-STOP은 `_try_update_state_from_msg` 안에서, 즉 **상태 프레임을 디코딩하는 도중에**
  트립된다. 어느 모터가 어떤 값으로 트립시켰는지가 사유에 들어있다.
- 트립 즉시 `disable_all()`이 호출되어 **토크가 0으로 떨어진다.** 그래프에서 갑작스러운
  토크 소실을 설명하는 유일한 신호다.
- 주의: `reset_estop_each_state_cycle`이 True라 **state_only 모드에서는 매 사이클 estop이
  클리어된다.** 그래서 estop이 깜빡이는 것처럼 보일 수 있는데, 이걸 모르면 로그 해석이
  꼬인다. `mode` 필드와 같이 봐야 한다.

**`damping`**

감쇠 전환 시 `kp=0`이 되므로 유지 토크가 사라지고 관절이 중력으로 처진다. 이 플래그가
없으면 "모터가 고장났다"로 오해한다. 특히 ROM 왕복 테스트 중에 발생하면 목표에 도달하지
못해 **옵션3의 "한 방향에서 멈춤" 증상과 똑같이 보인다.** 두 원인을 가르려면 이 플래그가
필요하다.

**`rejects` (명령 거부 수)** ← 가장 "보이지 않는" 실패

명령이 거부되면 `_prepare_mit_payload`가 `None`을 반환하고 `_send_action_all`은 그냥
`continue`로 **조용히 건너뛴다.** 전송 자체가 일어나지 않는다.

거부 지점은 네 곳이다:

| 원인 | 위치 |
|---|---|
| 유효 상태 없음 | `_prepare_mit_payload` (`st.stamp <= 0`) |
| 명령 한계 초과 | `_prepare_mit_payload` / `_passes_action_update_jump_guard` |
| 점프 과대 (`max_cmd_delta_deg`) | 동일 |
| 발목 IK 불가 | `set_leg_action`의 `AnkleUnreachableError` |

**그리고 `print`는 모터당 0.5초에 한 번으로 스로틀된다** (`_last_jump_warn_s`). 100Hz에서
200번 거부돼도 콘솔에는 1줄만 뜬다. 즉 **거부가 산발적인지 지속적인지 지금은 알 방법이
없다.** "명령을 보냈는데 안 움직인다"의 가장 흔한 원인이 여기다.

원인별로 나눠서 카운트하는 것을 권장한다 (`rejects_limit`, `rejects_jump`, `rejects_ik`,
`rejects_nostate`) — 합계만 보면 어느 가드가 걸렸는지 알 수 없다.

#### (5) 열 / 전기

**모터 온도 `temp`**

MIT 피드백 프레임 Byte6~7(°C×10)에 이미 있고 `mit_codec`이 이미 디코딩 중이다. 공짜다.

다리 제어에서 특히 중요한 이유:

- **자세 유지 = 지속 토크 = 발열.** 서 있는 자세를 유지하는 동안 모터는 계속 토크를 낸다.
  움직이지 않아도 뜨거워지는 상황이 기본값인 구조다.
- **RS02는 정격 6 N·m, 피크 17 N·m인데 17 N·m는 10초만 견딘다** (매뉴얼 p.4 최대 부하 곡선
  / Test data: 17→10s, 11→100s, 6.5→3000s, 6→rated). 즉 `tau`와 `temp`를 **같이 봐야**
  "지금 자세를 얼마나 오래 유지할 수 있나"가 나온다. 둘 중 하나만으론 판단할 수 없다.
- **과열 임계 135°C** (매뉴얼 fault bit0).
- 튜닝 세션이 길어지면 온도 상승으로 모터 특성이 변한다. 같은 게인인데 응답이 달라지는
  현상의 원인이 여기인 경우가 있다.

> **버스 전압·상전류(Iq)는 MIT 표준 프레임에 없다.** 아쉬운 이유: 토크는 전류에 비례하고
> (RS02 토크상수 1.22 N·m/Arms), 최대 상전류가 23 Apk이므로 **토크 상한(17 N·m)보다 전류
> 제한에 먼저 걸릴 수 있다.** 또 버스 전압 강하는 "토크가 안 나오는" 숨은 원인이다.
> RobStride private 프로토콜의 파라미터 읽기(Communication type 17)로 `0x300c VBUS`,
> `0x302c torque_fdb` 등을 저주기(1~10Hz) 폴링해 붙일 수 있다.

#### (6) 루프 / 통신 건전성 — 가장 자주 빠지는 분류

제어가 이상할 때 **원인이 제어기인지 통신인지** 가르는 것이 이 셋이다. 없으면 게인만 계속
만지게 된다.

**실제 루프 주기 `loop_dt`**

`control_hz=100`이 실제로 지켜지는지. 지금 `_run_loop`는 밀렸을 때 `next_tick`을 리셋하고
**따라잡기를 포기하는데, 아무 기록도 남기지 않는다.** 조용히 느려진다.

한 사이클의 작업량이 가볍지 않다는 점도 의심 근거다:

| 작업 | 비용 |
|---|---|
| `_drain_rx_states` | 마지막 `recv`가 항상 `None`을 기다리며 timeout(1ms) 소모 |
| 발목 IK (`solve_ik`) | 삼각 해석 + wrap |
| 발목 FK (`solve_fk`) | **뉴턴 반복 최대 120회** |
| CSV `flush()` | **매 사이클 디스크 I/O.** SD카드면 수 ms 튀는 게 정상 |

주기가 중요한 이유는 세 가지다:

1. **속도 상한을 정한다.** `_step_motor_toward_raw`는 사이클당 최대 `step_deg`만 전진한다.
   `실질 최대 속도 = step_deg × 루프주파수`이므로, 루프가 100→40Hz로 밀리면 **게인을 안
   건드렸는데 속도가 40%로 떨어진다.**
2. **원인 분리.** 루프가 밀려서 생긴 계단 모양 응답과 kd 부족으로 생긴 응답은 그래프에서
   비슷하게 보인다. `loop_dt`가 없으면 전자를 후자로 오해한다.
3. **MIT 명령 타임아웃.** RS02의 `CAN_TIMEOUT`(`0x200c`)이 켜져 있으면 명령이 끊긴 순간
   모터가 reset 모드로 빠진다. 기본값은 0(비활성)이지만, `move_motor10.py`도 "50Hz로 계속
   재전송(MIT 명령 타임아웃 방지)"이라고 이미 인지하고 있는 문제다.
4. **C++ 이식 판단 근거.** §2가 C++ 리팩토링을 전제로 하는데, 파이썬 루프의 실제 주기와
   지터가 그 판단의 정량적 근거다. 지금은 추측만 가능하다.

> 평균값은 거의 쓸모없다. 평균 10ms인데 가끔 50ms 튀는 것이 진짜 문제다.
> **최댓값·스파이크가 보이도록** 두고, 이동평균을 걸지 말 것.

**상태 나이 `age`**

마지막 상태 프레임 이후 경과 시간. 오래된 값으로 제어하고 있는지를 본다.

이 코드에서 실제로 발생할 수 있는 상황이다. 제어 모드에서 상태 요청은 **50 사이클마다
한 번**만 명시적으로 일어나고(`(self._cycle_idx % 50) == 0`, 0.5초 기준), 평소에는
`_send_action_all` 뒤의 응답 드레인에 의존한다. 응답이 안 오면 **최대 0.5초 묵은 값으로
제어가 계속된다.** 게다가 `_prepare_mit_payload`가 그 오래된 `cur_raw`를 기준으로 wrap을
해소하므로, 값이 낡으면 **엉뚱한 360° 표현을 고를 수 있다.**

**누락 모터 수 `n_missing`**

`_run_loop`가 이미 `missing` 리스트를 만들어 `_log_state`로 넘기고 있다. 특정 모터만
반복해서 빠지면 배선·CAN ID·종단저항 문제이고, 전체가 동시에 빠지면 버스 레벨 문제다.
이 구분이 그래프에서 바로 나온다.

> **현재 얻을 수 없는 것**: 고장 비트(과전류·과열·미교정·과부하)와 모드 상태
> (reset/cali/run)는 RobStride private 확장 프레임(Communication Type 2)의 29-bit ID에
> 실린다. 지금 쓰는 **MIT 표준 프레임(11-bit ID)에는 없다.** → §8 향후 확장

### 4.2 전송 포맷: UDP + JSON, 한 패킷 = 한 시점 스냅샷

```json
{
  "t": 12.345,
  "m10_pos": 10.2, "m10_tgt": 12.0, "m10_err": 1.8,
  "m10_vel": 3.1,  "m10_tau": 0.8,  "m10_temp": 34.5,
  "m10_kp": 30.0,  "m10_kd": 0.3,   "m10_margin": 62.6,
  "q_knee": 10.2,  "q_knee_tgt": 12.0,
  "estop": 0, "damping": 0, "mode": 1, "loop_dt": 10.1, "rejects": 0
}
```

**평면(flat) 구조를 유지한다.** 중첩 JSON도 PlotJuggler가 파싱하지만, 평면 쪽이
C++ 이식(§6) 때 직렬화가 단순하고 필드명 계약이 그대로 보존된다.

### 4.3 필드 정의

모터별 필드는 `m{id}_*` (id = 7,8,9,10,11,12), 관절공간은 `q_*`, 나머지는 전역.

**Tier 1 — 필수 (P1에서 바로 구현)**

| 키 | 의미 | 단위 | 출처 |
|---|---|---|---|
| `t` | 단조 시간(시작 기준) | s | `time.monotonic()` |
| `m{id}_pos` | 실측 위치 | deg | `state[id].position_deg` |
| `m{id}_tgt` | 목표(명령) 위치 | deg | `action[id].position_deg` |
| `m{id}_err` | 위치 오차 (`tgt − pos`) | deg | 파생 |
| `m{id}_vel` | 실측 속도 | deg/s | `state[id].velocity_deg_s` |
| `m{id}_tau` | 실측 토크 | Nm | `state[id].torque_nm` |
| `m{id}_temp` | 모터 온도 | °C | `state[id].temp_mos_c` |
| `estop` | E-STOP 상태 | 0/1 | `_estop` |
| `damping` | 감쇠 전용 모드 | 0/1 | `_damping_active` |
| `mode` | 0=state_only, 1=control | enum | `mode` |

**Tier 2 — 권장 (P2)**

| 키 | 의미 | 단위 | 출처 |
|---|---|---|---|
| `m{id}_kp`, `m{id}_kd` | 현재 게인 | — | `gains[id]` |
| `m{id}_margin` | 한계까지 최소 여유 | deg | `command_limits_cal_deg` |
| `loop_dt` | 직전 루프 실제 주기 | ms | `_run_loop` 계측 |
| `n_missing` | 이번 사이클 무응답 모터 수 | 개 | `missing` |
| `rejects` | 이번 사이클 거부된 명령 수 | 개 | 점프가드/클램프/IK 실패 카운터 (신규) |
| `estop_code` | E-STOP 사유 코드 | enum | `_estop_reason` → 정수 매핑 |

**Tier 3 — 선택 (P2 이후)**

| 키 | 의미 | 단위 |
|---|---|---|
| `q_{joint}` | 관절공간 실측각 (`hipz/hipx/hipy/knee/ankle_pitch/ankle_roll`) | deg |
| `q_{joint}_tgt` | 관절공간 목표각 | deg |
| `m{id}_age` | 마지막 상태 프레임 이후 경과 | ms |

### 4.4 구현 제약

- **스키마는 한 곳에서만 정의한다.** 지금 필드 목록이 `_open_log`의 CSV 헤더와 이
  문서 두 군데에 있고, 여기에 UDP가 세 번째로 추가되면 반드시 어긋난다. 컨트롤러에
  스냅샷 dict를 만드는 메서드를 하나 두고 **CSV와 UDP가 둘 다 그것을 소비**할 것.
- **PlotJuggler는 숫자만 그린다.** bool은 `0/1` 정수로, 문자열(`estop_reason`)은
  정수 코드로 변환해서 보낼 것. 원문 문자열은 CSV 로그에만 남긴다.
- **패킷 크기.** Tier 1~3 전부면 필드 약 80개 ≈ 1.3 KB로, 이더넷 MTU(1500B)에
  근접한다. 소수점 2자리로 반올림해 보내고, 1400 B를 넘기면 저주기 필드를 별도
  패킷으로 분리할 것. (UDP 단편화는 손실률을 키운다)
- **시간축**: PlotJuggler UDP 파서에서 `t`를 timestamp 필드로 지정한다. 지정하지
  않으면 수신 시각을 쓰게 되어 네트워크 지터가 데이터에 섞인다.
- 전송 주기: 제어/상태 읽기 주기에 맞춰 **50~200Hz** (JSON 소량이라 부담 없음).

## 5. 네트워크 구성

- **인터넷 불필요.** 파이와 우분투가 서로 닿는 **로컬 네트워크**만 있으면 됨.
- 연결 방식(택1):
  1. 같은 공유기(Wi-Fi/이더넷) — 가장 간단
  2. 랜선 직결(정적 IP) — 공유기 없이, 지터 최소
- 포트: UDP `9870` (변경 가능)
- 우분투 방화벽: `sudo ufw allow 9870/udp`
- 확인: `ping <우분투IP>` → `echo '{"t":1,"x":42}' | nc -u -w1 <우분투IP> 9870`

## 6. 구현 계획

### 원칙
- **제어 로직과 분리**: 텔레메트리는 독립 모듈(`telemetry.py`)로, 실패해도 제어에
  영향 없게(예외 무시, 논블로킹 소켓).
- **계약 고정**: UDP 포트 + JSON 필드명을 계약으로 삼는다 → C++ 전환 시 그대로 유지.

### 단계
1. **[P1] 텔레메트리 모듈** `telemetry.py` + Tier 1 필드
   - `UdpTelemetry(host, port)` : `send(dict)` 논블로킹 UDP 송신.
   - 대상 IP/포트는 인자·환경변수(`PJ_HOST`, `PJ_PORT`)로 주입.
   - 컨트롤러에 스냅샷 생성 메서드를 하나 두고 (§4.4) Tier 1 필드를 채운다.
2. **[P2] 컨트롤러 계측 지점 삽입** + Tier 2/3 필드
   - 상태를 읽는 지점(예: `_step_motor_toward_raw`, `_read_motor_pos`,
     그리고 향후 `_run_loop`)에서 스냅샷을 만들어 `telemetry.send(...)`.
   - 메뉴(옵션 2/3) 동작 중에도 값이 흐르도록.
   - `loop_dt` 계측과 `rejects` 카운터는 이 단계에서 컨트롤러에 새로 추가된다.
3. **[P3] 우분투 PlotJuggler 세팅 문서/프리셋**
   - UDP Server(JSON) 시작 → `t`를 timestamp 필드로 지정 → 필드 드래그 →
     자주 보는 레이아웃 저장(.xml 레이아웃).
4. **[P4] (선택) 로그 동시 저장**
   - 같은 스냅샷을 CSV로도 남겨 사후 리뷰/시뮬 비교.
   - 기존 `_open_log`/`_log_state`의 자체 헤더 정의를 스냅샷 소비로 교체 (§4.4).

### C++ 리팩토링 시
- 제어를 C++로 옮겨도, **같은 UDP 포트에 같은 JSON을 `sendto`** 하기만 하면
  PlotJuggler 설정·레이아웃은 그대로 재사용. (nlohmann/json 등으로 직렬화)

## 7. 사용법 요약 (Quick Start)

```bash
# [우분투] PlotJuggler 실행 → Streaming: UDP Server → Port 9870, JSON → Start

hostname -I                      # 우분투 IP 확인 (예: 192.168.0.50)

# [파이] 컨트롤러 실행 시 우분투 IP 지정 (구현 후)
```

## 8. 향후 확장

- **목표 vs 실측 겹쳐보기 레이아웃** 프리셋 저장(튜닝 표준 화면).
- **고장 비트 / 모드 상태**: RobStride private 확장 프레임(Communication Type 2)의
  29-bit ID에 과전류·과열·미교정·과부하 비트와 모드(reset/cali/run)가 실린다.
  지금의 MIT 표준 프레임으로는 못 받으므로, 필요해지면 private 프로토콜 병행 또는
  전환이 필요하다 (§4.1-(6)).
- **버스 전압 / 상전류(Iq)**: private 파라미터 읽기(type 17)를 저주기(1~10Hz)로
  폴링해 별도 채널로 추가 (§4.1-(5)).
- 이력 리뷰가 중요해지면 **Rerun**(3D 다리 자세 포함)이나 **MCAP 로깅** 병행.
- 알람(토크 임계 초과 등)은 제어 측 안전로직(E-STOP)이 담당하고, PlotJuggler는
  관찰 전용으로 유지.

## 부록: 왜 인터넷이 아니라 로컬 네트워크인가

UDP 텔레메트리는 파이 → 우분투의 **직접 IP 통신**이다. 공용 인터넷을 거칠 필요가
없고, 같은 LAN(또는 랜선 직결)에서 서로 IP로 닿기만 하면 된다. 오히려 로컬로
유지하는 편이 **지연·지터가 작고 안전**하다.
