# `motors/` — 모터 계층

```
motors/
├── base.py     벤더 중립 자료형과 인터페이스
├── canbus.py   CAN 전송
└── robstride/  RobStride 드라이버
```

## 이 계층이 아는 것과 모르는 것

**모터 id 와 raw 각도를 앎.** "10번 모터가 62.79°" 까지가 여기 어휘임.

**"무릎" 을 모름.** 관절 이름, cal 각도, 발목 두 모터가 하나의 관절이라는 사실은
전부 `robots/` 가 앎.

경계를 이렇게 그은 이유: 모터 배선은 다리마다 다르지만 관절 이름은 같음. 여기가
관절을 알면 왼다리와 오른다리에 서로 다른 드라이버가 필요해짐.

---

## `base.py`

`python-can` 을 import하지 않음. 자료형과 인터페이스만 있어 하드웨어 없이 돌아감.

### 적는 것과 재는 것을 나눔

```
Motor              사람이 적는 것. 배선·설계·튜닝에서 옴  ->  config/
MotorCalibration   조립을 재서 얻는 것                    ->  calibration/
```

**무효화 시점이 다름.** 모터를 다시 달면 `MotorCalibration` 만 무효가 되고, 기구
설계가 바뀌면 `Motor` 만 바뀜. 한 파일에 두면 한쪽을 고칠 때 다른 쪽을 덮어씀.

id 로 키를 맞춘 표를 여러 개 늘어놓지 않고 **모터 하나당 항목 하나**로 둠. 표가
나뉘어 있으면 모터를 추가할 때 한 표에만 넣고 다른 표에서 빠뜨릴 수 있음. 관절이
20개를 넘어가면 실제로 일어남.

### raw 와 cal

모터가 보고하는 각도(raw)와 사람이 말하는 관절 각도(cal)는 다름.

```
cal = wrap180(sign * raw + offset)
```

어긋나는 원인은 둘임.

**기준 자세가 다름 (`offset`)** — 다리가 무거워 `0xFE`(영점 설정)를 정확히 편
자세에서 누를 수 없음. 무릎을 12° 굽은 상태에서 영점 잡으면:

| 물리적 자세 | raw | cal |
|---|---|---|
| 완전히 편 상태 | −12 | 0 |
| 12° 굽힘 (영점 잡은 자세) | 0 | 12 |
| 하드스톱 | 62.79 | 74.79 |

**회전 방향이 다름 (`sign`)** — 양다리는 거울상이라 같은 굽힘에 raw 부호가 반대임.

| 물리적 자세 | 오른 무릎 raw | 왼 무릎 raw | cal (양쪽 동일) |
|---|---|---|---|
| 편 상태 | 0 | 0 | 0 |
| 45° 굽힘 | +45 | −45 | 45 |

**이것이 cal 공간이 존재하는 이유임.** 보행 궤적이 "무릎 45°" 라고 하면 양다리가
같은 동작을 함. raw 로 말하면 다리마다 부호를 뒤집어야 하고, 그걸 잊는 자리가 코드
곳곳에 생김.

> 감속비 항은 없음 — RobStride 는 출력축 각도를 보고하므로 배율이 필요 없음.
> `sign` 과 `offset` 두 개면 충분함.

경계는 `robots/` 임. 버스 위쪽은 전부 cal, 아래쪽은 전부 raw.

### 한계값은 `Motor` 에 cal 공간으로

```python
Motor(id=10, model="RS02", limits_deg=(-20.65, 74.79), gains=Gains(kp=30.0, kd=1.0))
```

관절 가동범위는 기구 설계에서 오는 값이라 첫 동작 **전에** 이미 알고 있어야 함.
움직여 보고 알아내는 값이 아님 — 다리를 손으로 하드스톱까지 훑는 것이 중력과
감속비 때문에 불가능하고, 발목은 두 모터가 폐루프로 물려 있어 한쪽만 훑으면 링크가
물림.

설계에서 오는 값이므로 **영점을 어디에 잡았는지와 무관함.** raw 에 두면 영점을 다시
잡을 때 숫자는 그대로인데 가리키는 물리적 위치가 달라짐.

`lo < hi` 를 `__post_init__` 에서 검사함. cal 공간에는 `sign` 이 개입하지 않아
순서가 뒤집히지 않으므로, 변환할 때마다 `min/max` 로 재정렬할 필요가 없음.

**`None` 은 "제한 없음" 이 아니라 "아직 모름" 임.** 한계를 모르는 채로 토크를 넣는
것이 가장 위험하므로 `is_configured` 가 `False` 가 됨.

### `Gains` 를 캘리브레이션에서 뺀 이유

```
sign, offset   조립을 재면 나오는 값     <- 실측
kp, kd         돌려보며 맞추는 값        <- 튜닝
```

모터를 다시 달면 `offset` 은 무효지만 게인은 그대로 쓸 수 있음. 반대로 페이로드가
바뀌면 게인만 다시 잡음.

`scaled()` 는 브링업 초반에 전체를 한꺼번에 낮추는 데 씀. `kp` 만 낮추면 감쇠비가
달라져 발진함.

**기본값 0은 토크 없음임.** 실측 전에 움직이지 않도록 일부러 0으로 둠.

### `MotorState` — 신선도

```python
st.age(now)                    # 마지막 갱신 이후 흐른 초
st.is_fresh(now, max_age_s)    # 제어에 쓸 만큼 최신인지
```

점프 가드는 "지금 위치" 를 기준으로 자르는데, 그 기준이 몇 주기 전 값이면 실제로는
큰 점프를 통과시킴.

`stamp` 는 `time.monotonic()` 임. 벽시계는 NTP 보정에 뒤로 갈 수 있어 나이 계산이
음수가 됨.

### `MotorsBus` — 런타임 조작만

```
motor_ids / is_connected
connect / disconnect        + 컨텍스트 매니저
enable_torque / disable_torque
refresh_states              응답이 없었던 id 리스트를 반환
state / states
```

되돌리기 어려운 1회성 조작(CAN ID 변경, 프로토콜 전환, 기계영점, 플래시 저장)은
**여기 없음.** 벤더별 `commissioning` 모듈로 격리함 — 제어 루프에서 실수로 호출될
수 있는 자리에 두면 안 되는 것들임.

컨텍스트 매니저를 계약에 넣은 이유: 제어 중 예외가 나면 모터가 마지막 명령을 계속
유지함. 사람이 전원을 뽑을 때까지 다리가 힘을 주고 있음.

`refresh_states` 가 예외를 던지지 않는 이유: 한 모터가 한 주기 빠지는 것은 흔한
일이고, 그때마다 루프가 죽으면 안 됨. 호출부가 몇 주기 연속인지 보고 판단함.

## `canbus.py`

프레임을 **주고받기만** 함. 안에 든 바이트가 무슨 뜻인지 모름.

`python-can` 을 import하는 **유일한 파일**임. 위 계층은 `CanFrame` 만 다루므로,
드라이버를 바꾸거나 테스트에서 가짜 버스를 끼울 때 이 파일만 보면 됨.

`import can` 이 함수 안에 있음. 모듈 최상단에서 하면 이 파일을 import하는 것만으로
`python-can` 이 필요해지고, 순수 계산 계층의 테스트까지 같이 막힘.

### 채널은 이 코드 밖에서 올라옴

socketcan 채널은 커널이 관리함. 속도를 포함한 설정이 채널을 올릴 때 정해지고, 이
코드는 이미 올라와 있는 채널에 붙기만 함.

```bash
sudo ip link set can0 up type can bitrate 1000000
```

### 전송과 수거가 별개임

```python
left.send_many(frames_left)      # ① 전송을 먼저 몰아서
right.send_many(frames_right)
drain_all([left, right])         # ② 그 다음에 수거
```

한 덩어리로 묶여 있으면 버스가 둘일 때 두 다리의 명령 시각이 벌어짐 (이슈 #10).

```
왼다리  [보내기][─── 수거 대기 ───]
오른다리                          [보내기]
                                  ↑ 여기서야 시작
```

두 버스는 물리적으로 독립이라 전송이 진짜로 겹치는데, 묶여 있으면 그 병렬성을
못 씀. **수거가 더 비쌈** — `recv()` 는 큐가 비면 타임아웃만큼 블로킹하므로 순차로
수거하면 그 시간이 버스 수만큼 곱해짐.

### 드레인 비용

100Hz 루프의 예산은 10 ms 임. 그 안에서 `recv(timeout=2ms)` 를 한 번 부르고 큐가
비어 있으면 **2 ms 를 그냥 버림.**

그래서 짧게 여러 번 폴링하고, 기다릴 총 시간을 따로 둠.

```python
bus.drain(expect=6, timeout_s=0.002, poll_s=0.0002)
```

기대한 개수가 다 오면 즉시 빠져나감 — 정상 상황에서는 총 시간을 다 쓰지 않음.

마감은 **기다릴 때만** 봄. 이미 큐에 있는 것은 마감과 무관하게 다 읽음.

### `send_many` 가 락을 한 번만 잡음

프레임마다 잡았다 놓으면 그 사이에 다른 프레임이 끼어들어 한 다리의 명령 6개가
버스에서 흩어짐.

**중간에 실패해도 나머지를 계속 보냄.** 첫 프레임이 실패했다고 멈추면 나머지 5개가
직전 명령을 유지해 자세가 어긋남.

### `flush_rx`

직전 주기의 응답이 남아 있으면 이번 주기의 것으로 오해함. 특히 고장 조회는 일반
상태 프레임과 CAN ID 가 같아 구분되지 않으므로, 보내기 전에 비워야 함.

### 집계

```
can.tx_errors  can.rx_errors  can.frames_sent  can.frames_received  can.drain_timeouts
```

한 번의 실패는 흔한 일이라 예외를 던지지 않음. **몇 번 연속인지**가 의미 있고, 그
판단은 호출부가 함.

0이어도 모든 키를 냄. 필드가 중간에 생기면 그래프가 끊김.

### 스레드

지금은 제어 루프 한 곳에서만 부름. 송신에만 락을 걸어 프레임이 섞이지 않게 함.

**수신 전용 스레드를 두면 이 가정이 깨짐.** 수신 스레드가 락을 쥔 채 `recv` 에서
블로킹하면 송신이 그만큼 밀리므로, 그때 락 구성을 다시 봐야 함.

## 하드웨어 전제

코드가 확인하지 않고 **맞다고 가정하는 것들**임. 어긋나면 조용히 잘못 동작함.

| 전제 | 확인 | 어긋나면 |
|---|---|---|
| MIT 프로토콜 (11-bit 표준 프레임) | `PARAM_PROTOCOL_FLAG` `0x201F` | **명령이 무시되고 에러도 안 남** |
| `zero_sta = 1` | `PARAM_ZERO_STA` `0x7029` | 위치 보고가 `[0,360)` 이 되어 부호가 뒤집힘 |
| 비트레이트 1 Mbps | `ip -details link show can0` | 통신이 아예 안 됨 |
| CAN id 가 설정과 일치 | 한 개씩 움직여 확인 | 다른 관절이 움직임 |

**프로토콜 모드가 가장 위험함.** 공장 기본값은 private(29-bit 확장)인데 이 코드는
MIT 로 보냄. 안 맞으면 연결도 되고 코드도 안 죽는데 모터만 안 움직임 — 진단이 가장
어려운 종류의 실패임. 전환에는 **전원 재투입**이 필요함.

`zero_sta` 는 플래시에 저장됨. 위치 보고 범위를 `[-180,180)` 으로 만드는 값이고,
모든 관절 한계가 ±180 안에 있으므로 이 전제 위에서 각도 감싸기 처리가 필요 없음.

**모터를 교체하거나 추가할 때마다 다시 설정해야 함.** 팔·상체로 확장하면 모터가
20개를 넘어가므로 스크립트로 일괄 확인·설정하는 것이 필요해짐.

## 벤더를 추가한다면

```
motors/
├── base.py       그대로
├── canbus.py     그대로 (CAN 을 쓰는 벤더면)
├── robstride/
└── 새벤더/
    ├── tables.py
    ├── codec/
    └── bus.py
```

`base.py` 에 **어느 벤더에도 특유하지 않은 개념만** 둔 이유임. 인코딩 범위
(`pmax`/`vmax`/`tmax`) 같은 것은 MIT 류 프로토콜 특유의 개념이라 `robstride/` 에
있음 — CANopen 계열은 pulse 단위를 쓰고 인코딩 범위라는 개념 자체가 없음.

`Motor.model` 이 `str` 인 것도 같은 이유임. 여기서 enum 으로 좁히면 벤더를 추가할
때마다 중립 계층을 고쳐야 함. 유효한 모델인지는 벤더 버스가 생성자에서 판단함.
