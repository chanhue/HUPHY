# `kinematics/` — 기구학

```
kinematics/
└── ankle.py   발목 2모터 링키지. 관절각 <-> 모터각
```

순수 계산임. 모터도 CAN 도 모르고 숫자만 다룸. `numpy` 만 씀.

---

## 왜 발목만 있나

다른 관절은 **모터 하나가 관절 하나**를 돌림. 무릎에 30도를 보내면 무릎이 30도
돎 — 변환할 것이 없음.

발목은 다름. **모터 두 개가 로드 두 개로 발판 하나를 밀고 당김.**

```
a1 ↑  a2 ↓     ->  발끝이 내려감 (pitch)
a1 ↑  a2 ↑     ->  발이 옆으로 기움 (roll)
```

그래서 "pitch 10도" 를 모터 각도 두 개로 풀어야 하고, 모터 각도 두 개를 읽으면
지금 pitch/roll 이 얼마인지 계산해야 함.

---

## 두 방향

```python
solve_ik(pitch, roll)  ->  (a1, a2)      역기구학
solve_fk(a1, a2)       ->  (pitch, roll) 순기구학
```

### 비용이 다름

`solve_ik` 는 **닫힌 해**임. 삼각함수 몇 번으로 끝남. 제어 루프에서 매 주기 불러도 됨.

`solve_fk` 는 **뉴턴 반복**임. 두 로드 길이가 동시에 맞는 자세를 수치로 찾아감.

명령은 IK 로 내려가고, **FK 는 사람에게 보여줄 때만** 씀.

---

## FK 는 답이 하나가 아님

**같은 모터각 조합이 서로 다른 자세 둘에 대응함.**

```python
a1, a2 = ankle.solve_ik(90, 90, enforce_envelope=False)   # (52.10, 45.41)

ankle.solve_fk(a1, a2)                                    # (2.41, -40.48)
ankle.solve_fk(a1, a2, guess_pitch_deg=90, guess_roll_deg=90)   # (90.00, 90.00)
```

둘 다 **맞는 해임.** 링키지의 성질이지 버그가 아님. 어느 쪽으로 수렴할지는 초기
추정이 정함.

### 실제로는 문제가 안 됨

시험 범위 안에서는 추정 `(0, 0)` 으로도 **항상** 원래 자세를 찾음. 격자 187개로
확인함 (`test_default_guess_is_enough_inside_the_envelope`).

제어 루프에서는 한 주기 전 자세를 추정으로 넣으면 됨 — 늘 가까움.

**범위를 넓히면 이 성질이 깨질 수 있음.** 그때 다시 확인할 것.

### 발산은 막음

수렴한 답을 **IK 로 되짚어 확인함.** IK 는 닫힌 해라 싸고, 이 검사가 없으면 발산한
값이 그대로 나감.

```python
ankle.solve_fk(170.0, -170.0)     # AnkleUnreachableError
```

NaN 을 돌려주면 `safety.guards` 가 잡기 전까지 조용히 흘러감.

---

## 각도 규약

두 모터 각도를 **모두 `[-180, 180)`** 으로 냄.

모터가 `zero_sta = 1` 로 그 범위를 보고하기 때문임. 한쪽만 `[0, 360)` 으로 두면
IK 가 340도를 돌려주고 모터는 -20도를 보고해 **360도 차이**가 남 (이슈 #1).

이 규약이 맞아떨어져서 별도의 각도 감싸기 처리가 필요 없음 — 모든 관절 한계가
±180 안에 있고 전 회전을 하지 않음.

---

## 닿지 않는 자세는 던짐

```python
ankle.solve_ik(80.0, 0.0, enforce_envelope=False)
# AnkleUnreachableError: ... 로드 해가 없음 (a1 가능=False, a2 가능=True)
```

자르지 않는 이유: 발목은 두 모터가 물려 있어 **한쪽만 잘리면 관절이 비틀림.**
무엇을 보낼지는 상위가 정해야 함.

어느 로드가 안 닿는지 같이 알려줌.

### 시험 범위는 별개임

```python
AnkleEnvelope(roll_deg=(-25, 25), pitch_deg=(-40, 40))
```

링키지가 닿는 범위보다 **좁게** 잡아 둔 소프트웨어 값임. 브링업 단계라 보수적으로
감. `enforce_envelope=False` 로 건너뛸 수 있고, `is_reachable()` 은 범위를 무시하고
링키지만 봄.

시험 범위 네 귀퉁이가 전부 닿는지 테스트가 확인함 — 안 닿으면 설정이 잘못된 것임.

---

## 거울상

```python
left = AnkleKinematics(AnkleGeometry().mirrored())
```

**좌표만 뒤집으면 안 됨.** `crank_t` 는 x 방향 오프셋이라 부호가 같이 뒤집혀야 하고,
모터 회전축이 x 축이므로 yz 평면 반사에서 회전 방향도 뒤집힘.

제대로 뒤집으면 다음이 정확히 성립함.

```
거울상.solve_ik(pitch, -roll) == -원본.solve_ik(pitch, roll)
```

**이게 성립해야 보행 궤적 한 벌로 양다리를 움직일 수 있음.** 좌표만 뒤집으면 이
관계가 근사로만 맞아 좌우가 미묘하게 다르게 움직임.

## 기하값

```
a1     (-26.10,  74.000, -255.00)   모터 1 회전축
a2     (-80.90,  74.000, -313.00)   모터 2 회전축
origin (-53.50,  74.000, -393.00)   발목 회전 중심
c1     ( -8.10, 111.343, -398.00)   로드 1 이 발판에 붙는 곳
c2     (-98.90, 111.343, -398.00)   로드 2 가 발판에 붙는 곳

crank_r  40.0    모터 디스크 반지름
crank_t  18.0    디스크가 축에서 x 방향으로 떨어진 거리
```

단위는 mm. 모터 회전축은 x 축이고 디스크는 y-z 평면에 놓임.

**로드 길이는 여기 없음.** 중립 자세(모터각 0)에서 계산됨 — 143.02 와 85.04.
좌표를 고치면 길이도 따라 바뀌므로 따로 관리할 값이 아님.

두 로드 길이가 크게 다름. **대칭 링키지가 아님.**

### 출처가 확인되지 않음 (이슈 #13)

실물 발목 **하나**를 실측한 값임. 어느 쪽 다리인지 기록이 없고, 반대쪽은
`mirrored()` 로 만든 계산 결과임 — 실측이 아님.

`rotation_sign_1/2` 가 실물과 맞는지도 확인된 바 없음. 반대면 발목이 목표에서
멀어지는 방향으로 감.
