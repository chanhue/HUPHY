# `safety/` — 한계와 명령 가드

전부 순수 함수임. 상태를 갖지 않고 CAN도 락도 모름. 숫자를 받아 숫자를 돌려줌.

```
safety/
├── limits.py   한계와의 관계를 계산      (사실)
├── guards.py   명령을 통과시킬지 결정    (판단)
└── link.py     응답이 오고 있는지 판정   (판단)
```

`guards` 가 **값**을 보고, `link` 가 **응답**을 봄. 둘 다 명령이 나가기 전에
걸리지만 근거가 다름.

하드웨어 없이 테스트됨.

```bash
PYTHONPATH=src python3 -m pytest tests -q     # python-can 불필요
```

계층 규칙 확인 명령:

```bash
grep -rhn "^import \|^from " src/huphy/safety/*.py | grep -v ":from \."
# 표준 라이브러리만 나와야 함 (math / typing / dataclasses / enum)
```

## 두 파일의 역할 분담

| | `limits.py` | `guards.py` |
|---|---|---|
| 하는 일 | **사실 계산** | **판단** |
| 예 | "한계에서 5° 남음" | "그러므로 보냄 / 자름" |
| 아는 것 | 각도 하나, 한계 하나 | 목표 + 현재 + 제약 전부 |
| 호출 시점 | 여러 곳 | 명령 전송 시에만 |

`limits`는 "5° 남음"까지만 계산함. 그걸로 무엇을 할지는 호출부가 결정.

`guards`가 `limits`를 사용. 역방향 의존 없음.

## `limits.py`

### 공간 규약

모든 각도는 **raw 공간** — 모터가 보고하는 각도 그대로. `sign`/`offset`을 적용한
calibrated 공간이 아님.

한계값은 무동력으로 하드스톱까지 밀어 raw를 읽어 얻으므로 raw가 자연스러움.
사람에게 표시할 때만 calibrated로 변환.

### `limits`는 하드스톱 실측값

`(lo, hi)`는 **기계적으로 더 갈 수 없는 지점**의 실측값임. 안전 여유가 이미 빠진
값이 아님. 따라서 여유는 하드스톱에서 **안쪽 방향**으로 뺌.

```
하드스톱                                    하드스톱
   │---3°---│                    │---3°---│
   │      명령 허용 구간           │
   lo                            hi
```

### 여유를 두는 이유

**명령을 하드스톱에 정확히 두면 부딪힘.**

| 원인 | 내용 |
|---|---|
| **오버슛** | PD 제어는 목표를 지나침. kd가 충분해도 0은 아님 |
| **관성** | 고속 이동 중 명령을 멈춰도 즉시 정지하지 않음 |
| **측정 오차** | 하드스톱 실측이 실제보다 크면 여유 없이는 닿음 |

> **3°는 임의값임.** 게인 튜닝 후 목표를 한계 근처로 보내 텔레메트리에서 오버슛
> 크기를 측정하고, 안전계수를 더해 확정할 것.

### 함수

| 함수 | 반환 |
|---|---|
| `safe_window(limits, margin)` | 여유만큼 안쪽으로 좁힌 구간 |
| `clamp(deg, limits, margin)` | `(자른 값, 잘림여부)` |
| `margin_to_limit(deg, limits)` | 가까운 쪽 한계까지 남은 여유. 초과 시 음수 |
| `closest_to_limit(values, limits)` | 가장 아슬아슬한 `(모터 id, 여유)` |

무릎(`-20.65 ~ 74.79`) 예시:

```python
safe_window(knee, 3)              # (-17.65, 71.79)
clamp(90, knee, margin_deg=3)     # (71.79, True)   잘림
clamp(50, knee, margin_deg=3)     # (50.0, False)   그대로
margin_to_limit(50, knee)         # 24.79
margin_to_limit(80, knee)         # -5.21           음수 = 초과
```

**`clamp`이 `(값, 잘림여부)`를 반환하는 이유** — 클리핑은 조용한 변조임. 잘렸는지
알리지 않으면 아무도 인지하지 못함. 순수 함수를 유지하면서 호출부가 카운터를 올릴
수 있음.

**`margin_to_limit`가 절대 각도보다 나은 이유** — 한계가 모터마다 다르고
비대칭이라(`-20.65 ~ 74.79`) 절대각을 보며 매번 암산해야 함. margin은 **0선 하나만**
보면 됨.

**`closest_to_limit`가 id를 함께 반환하는 이유** — 여럿 중 어느 관절이 문제인지
알아야 원인 추적이 가능함.

### 별도 파일인 이유

`guards` 외에도 소비자가 있음.

```
guards.apply()        위치 제한 클리핑          ← 명령 경로
telemetry             m{id}_margin 필드         ← 매 사이클
브링업 메뉴            현재 자세 정상 여부        ← 사람이 확인
```

**명령을 보내지 않는 관찰 모드에서도 한계와의 거리는 필요함.** `guards` 안에 두면
관찰 코드가 명령 검사기를 호출해야 하는 구조가 됨.

## `guards.py`

**"이 명령을 모터로 보내도 되는가, 보낸다면 어떤 값으로."**

여기를 통과한 값이 **그대로 CAN 프레임에 실림.** 마지막 방어선.

```python
r = guards.apply(target, current, limits=lim,
                 command_margin_deg=3, max_delta_deg=50)
if r.sendable:
    send(r.value)
counters.record(r)
```

### 세 관문

| 순서 | 관문 | 미통과 시 |
|---|---|---|
| 1 | **유한값** — 계산 결과가 숫자인가 | 거부 |
| 2 | **위치 제한** — 갈 수 있는 곳인가 | 클리핑 |
| 3 | **점프** — 한 번에 가도 될 폭인가 | 클리핑 |

### ① 유한값 검사가 최우선인 이유 ★

**파이썬의 `min`/`max`는 NaN을 비교할 수 없어 그대로 통과시킴.**

```python
min(10, nan)  # 10        ← nan < 10 이 False라 10 유지
```

따라서 인코딩 단계의 클램프가 **무력화됨.**

```python
float_to_uint(nan, -12.57, 12.57, 16)  # 65535 = 최대값 = 720°
```

**NaN 하나가 720° 목표 명령이 됨.** 조용히, 에러 없이.

발생 경로 — 발목 IK 뉴턴 반복 발산, 0으로 나누기(`sign=0`), 센서 이상값.
**클리핑으로 고칠 수 없으므로 거부함.**

### ② 클리핑 순서 — 한계 먼저, 점프 나중

**"안전한 목표를 정하고, 거기로 가는 속도를 제한한다"** 순서임.
역순이면 점프 제한을 통과한 값이 여전히 한계 밖일 수 있음.

**출력이 한계 밖일 수 있음.** 현재 위치가 이미 한계 밖이면(사고 후 복구 중) 한 번에
돌아오지 않고 `max_delta`씩 복귀함. **의도된 동작임.**

### ③ 버리지 않고 자르는 이유

버리면 **그 모터만 직전 명령을 유지해 다리 자세가 어긋남.** 발목처럼 2모터가
연동된 곳에서 특히 나쁨 — a1만 거부되면 pitch/roll이 어긋남.

점프는 특히 그러함.

```
버리면:    목표가 100° 떨어져 있으면  →  도달 불가
클리핑:    50 → 100 → 도달           →  2사이클
```

**클리핑 = 속도 제한.**

### `GuardResult`

```python
@dataclass(frozen=True)
class GuardResult:
    value: Optional[float]                 # None이면 전송 안 함
    reject: Optional[RejectReason] = None
    clips: Tuple[ClipReason, ...] = ()
    sendable: bool                          # property
```

`clips`가 **튜플**인 이유 — 한계와 점프가 **동시에** 걸릴 수 있음.

| | 값 | 전송 |
|---|---|---|
| `ClipReason` | `limit`, `jump` | **됨** (잘린 값으로) |
| `RejectReason` | `nan`, `nostate` | **안 됨** |

### `GuardCounters`

```python
counters.reset()               # 매 사이클 시작
counters.record(result)
counters.as_fields()
# {"clips": 3, "rejects": 1,
#  "clips_limit": 2, "clips_jump": 1,
#  "rejects_nan": 1, "rejects_nostate": 0}
```

**"잘림"과 "미전송"은 다른 사건**이므로 분리해 집계함. 합계만으로는 어느 관문이
걸렸는지 알 수 없음.

**0이어도 모든 키를 출력함.** 필드가 나타났다 사라지면 PlotJuggler 레이아웃과
CSV 헤더가 깨짐.

> `rejects_nan`이 0이 아니면 **어딘가 계산이 발산 중**이라는 뜻임.
> 조용히 720°로 가는 대신 그래프에 나타남.

## `link.py` — 통신이 끊겼나

`guards` 가 "이 명령을 내보내도 되나" 라면, 이쪽은 "명령이 도착하고 있나" 임.

### 왜 필요한가

MIT 모드는 명령을 받으면 **반드시** 상태 프레임으로 답함. 안 오면 그 모터가
명령을 처리하지 않은 것임 (이슈 #11).

한 주기 빠지는 것은 흔함 — 다음 주기에 옴. 문제는 **이어질 때**임.

```
현재 위치를 모름       가드가 명령을 거부함 (reject_nostate)
마지막 명령을 유지함    힘은 계속 나가고 있음
```

다리 하나면 그 관절만 굳음. **양다리면 로봇이 넘어짐** — 한쪽은 명령을 따라
움직이고 다른 쪽은 마지막 자세로 버팀.

### 주기 수로 셈

시간이 아니라 연속 무응답 주기 수로 판정함. 루프가 밀리면 시간 기준은 같은
상황을 다르게 판정하는데, 주기 수는 "몇 번 명령했는데 몇 번 답이 없었나" 라서
루프 속도와 무관하게 뜻이 같음.

세는 것은 로봇이 이미 함 (`link_status` 의 `miss`). 여기서 또 세면 같은 것을 두
군데서 세게 되고 한쪽만 초기화되는 일이 생김.

```python
LinkWatch(5).check(leg.link_status())    # None 이거나 LinkLoss
```

| 설정 | |
|---|---|
| `SafetyConfig.link_loss_cycles` | 몇 주기까지 봐주는지. 기본 5 (100Hz 에서 50ms) |
| `0` | 판정하지 않음. **커미셔닝 전용** — 응답이 원래 드묾 |

### 여기서 멈추지 않음

판정만 함. 실제로 세우는 것은 제어 루프임 — 정지는 자세를 붙잡고 토크를 끊는
순서가 있어서, 그 순서를 아는 곳에서 해야 함. 제어 모드에서만 봄.

**한 모터라도 걸리면 끊긴 것으로 봄.** 다리가 통째로 죽는 것만 위험한 게 아니고,
무릎 하나가 굳어도 그 다리는 의도한 자세를 못 만듦.
